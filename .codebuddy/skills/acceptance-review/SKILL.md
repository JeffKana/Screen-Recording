# 验收（Acceptance Review）

## Overview

验收是闭环里唯一有权写「通过」的环节。它不是复读执行报告，而是**独立重跑 + 逐项对照原文 + 五轴定级 + 回写留痕**。

一份合格的验收交付包含四样东西，缺一不可：

| 产出 | 内容 | 落到哪 |
| --- | --- | --- |
| **验收报告** | 逐项判定 + 门判据对照 + DoD 勾选 + 评分 + 等级 | `.codebuddy/plans/` |
| **findings 台账** | 每条带严重度、复现、remedy、归属 | 验收报告内 |
| **台账回写** | `docs/07-执行台账.md` 七列，结论列与实测一致 | 项目文档 |
| **下一轮指令** | 范围 / 优先级 / 验收标准 / 注意事项 / 通过判据 | `.codebuddy/plans/` |

> **一句话标准**：验收 = 独立重跑 + 逐项对照原文 + 五轴定级 + 结论回写台账 + 下发下一轮指令。

## When to Use

**使用**：收到执行报告 / 交付包（`tasks/{门}/{角色ID}-{序号}/`）需要出验收结论；某个门要关闭；需要判断某个挂账项能否关闭。

**不使用**：
- 要写实现代码 → 那是执行侧
- 要切任务卡 / 排期 → 那是规划侧
- 只是要跑一遍回归看绿不绿 → 直接跑 `verify/cases/`，不需要走验收流程

## 独立性硬约束

这六条是硬约束，违反其中任意一条，本轮验收结论无效。

| 约束 | 落地检查 | 违反后果 |
| --- | --- | --- |
| **执行者不自证** | 不得引用执行报告中的「通过」结论，必须自己跑命令拿输出 | 验收退化为复读，闭环失真 |
| **证据先于结论** | 每条判定附「命令 + 原始输出 + 时间戳」 | 无证据即视为未通过 |
| **不改被测物** | 不改 `src/`、不改 `verify/` 下用例、不改被测产物 | 改尺子 → 本轮作废 |
| **不解释需求** | 验收要点有误 → 提「文档缺陷单」，由规划侧决策 | 自行下调要点 → 结论宽于证据 |
| **归因分责** | 每条问题归到 执行者 / 规划 / 环境 三方之一 | 把规划失误记执行者账上 → 后续任务卡「少写少错」 |
| **结论不得宽于证据** | 实测数值必须原样回写结论列 | 台账漂移，事实源失效 |

> 「执行者不自证」在通用技能里对应 `code-review-and-quality` 的 Multi-Model Review Pattern：作者不能审自己，因为作者对自己的盲点是盲的。

## 门禁：PR / CI 先行（SOP 第 0 步）

> 与 `docs/20-研发协作SOP.md` 对齐。**门禁不过，验收不启动**——直接退回，不写验收报告、不记台账。

| 检查 | 通过条件 | 不通过 |
| --- | --- | --- |
| PR 存在 | base = `main`，head = `round/<NN>` | 无 PR → 不受理（直接推 main 的一律退回） |
| PR 描述 | 模板五项齐全（卡清单 / 需求-证据 / 自测 / 未做 / 风险） | 缺项 → 退回补齐，不计轮次 |
| CI | `checks` / `build (msvc)` / `build (mingw)` 全绿 | 任一红 → 退回执行方修复 |
| 改动范围 | `git diff main...round/NN` 不越卡内文件域 | 越界 → 要求补卡申报或回退 |
| 产物洁净 | 无 `build-*/`、`*.mkv`、`*.part`、`artifacts/` | 有 → 要求从分支移除 |

验收对象是**分支内容**（`git diff`），不是 PR 描述，也不是执行报告。

## The Process

### Step 1 · 理解上下文

按顺序读，**不要先读执行报告**（会被报告的叙事框住）：

1. `tasks/{门}/{角色ID}-{序号}/TASK.md` —— 需求范围、验收要点引用、必读章节、文件域
2. `../../../docs/01-功能需求清单.md` —— **验收要点原文**（不采信任务卡的转述）
3. `../../../docs/05-非功能需求与验收.md` —— 对应用例的判据原文
4. `../../../CONTRACT.md` —— 对应门判据章节
5. `../../../docs/06-子智能体执行规程.md` —— 验收标准与角色边界

**产出**：`待验需求清单`（需求号 → 验收要点原文 → 判据来源章节）。

### Step 2 · 先看测试，并做变异实验

- 测试是否**测行为**而非实现细节？用例名是否描述性？
- 新增断言是否**先在旧产物上跑红**？旧值是否入台账？
- **变异实验**：对关键断言反转一个条件（去否定、`&&` 换 `||`），跑一遍。
  变异后仍绿 → **这是一个 finding**，指出缺哪个测试用例名。
- 回归面：跑全量还是抽样，依据文件域；抽样必须说明依据。

**产出**：`测试充分性结论`（含变异实验结果表）。

### Step 3 · 逐项判定 + 五轴审查

对每条需求独立判定，**四档**：

| 结论 | 判定条件 | 计分 |
| --- | --- | ---: |
| **PASS** | 证据存在 + 现象符合验收要点 + 可复现 | 1.0 |
| **PARTIAL** | 主路径可用，边界/异常场景未覆盖 | 0.5 |
| **FAIL** | 现象不符或证据缺失 | 0 |
| **BLOCKED** | 依赖未就绪，无法验证（缺机型/缺环境） | 不计入分母 |

判定细则：
1. **证据缺失一律 FAIL**，不接受「代码看着像对」。
2. 验收要点含数值的，**必须给出实测值**（如「≤100ms」→ 报告实测 63ms）。
3. 同一需求多次运行结果不一致 → **PARTIAL** + 标「不稳定」，评估中双倍扣分。
4. **不得自行下调验收要点**。
5. **新断言必须先红后绿**：只在当前代码上跑绿不算证据，只能标「回归护栏」。

同时对被改动的代码/产物走五轴（correctness / readability / architecture / security / performance），
映射关系与评分公式见 `references/findings-rubric.md`。

**产出**：`逐项判定表`（需求号 | 结论 | 实测值/证据 | 备注）。

### Step 4 · 定级 findings

项目规程只在**需求级**有四档结论；**finding 级必须有严重度标签**，否则执行方分不清「必改」和「建议」。

每条 finding 带 **4 要素**：

```
[严重度] 定位: 文件:行 / 需求号
          现象: 观察到的事实（带数值）
          复现: 命令 + 输出
          remedy: 具体动作 ← 缺此项即为无效 finding
```

| 标签 | 含义 | 执行方动作 |
| --- | --- | --- |
| **Critical** | 阻断：安全漏洞、数据损坏、功能破坏、**结论列宽于证据** | 必须修，并重新验收 |
| *(无前缀)* / **Required** | 必改：与需求不符、缺证据、契约违规 | 合并前必须解决 |
| **Optional** / **Consider** | 建议 | 可不做，需给理由 |
| **Nit** | 风格细节 | 可忽略 |
| **FYI** | 仅告知 | 无动作 |

**remedy 必须落到结构动作，不能只描述问题。** 词表见 `references/findings-rubric.md`。

**产出**：`findings 台账`（标签 | 定位 | 现象 | 复现 | remedy | 归属）。

### Step 5 · 验证验证

- [ ] 测试跑了哪些、结果？
- [ ] 构建：Release + Debug 都过？零告警？
- [ ] 回归：无失败？抽样依据是什么？
- [ ] 手工验证（UI 改动需截图 / 前后对比）？
- [ ] 门判据（CONTRACT 对应章节）逐条对照？
- [ ] Definition of Done 的 Correctness / Quality 两节过了？
- [ ] 文档已同步（接口 → CONTRACT；结论 → 台账）？

**产出**：`门判据对照表` + `DoD 勾选表`。

### Step 6 · 结论回写与派发

**这一步最常被漏掉，但没有它闭环就断了。**

1. **回写 `../../../docs/07-执行台账.md`**：七列，一轮一行。结论列必须与实测一致（PARTIAL 就写 PARTIAL，并附未完成原因）。
2. **回写 `../../../docs/09-V1.0覆盖表.md`**：覆盖状态与实现状态一致。
3. **产出下一轮指令**：范围 / 优先级 / 验收标准 / 注意事项 / 通过判据。
4. **评分与归因**：A/C/E/K 四维 + 根因归属。

**产出**：台账回写 + 下一轮指令。

### Step 7 · 合并与收尾（SOP 第 7 环）

验收通过后，**合并权在 O0**，验收方只给结论、不自己合：

1. **合并**：`git merge --no-ff round/<NN>`，信息写 `round <NN>: <一句话>（S=xx.x）`；不 squash（轮次拓扑比线性历史值钱）。
2. **打 tag**：里程碑 `v0.x.y-baseline`，或轮次 `round-<NN>`。
3. **删分支**：远端与本地都删，避免残留分支指向已合并内容。
4. **回写**：`docs/07` 一行、`docs/09` 覆盖表、`docs/08` 轮次状态。
5. **下发**：合并完成后才发布下一轮卡——执行方永远从新 main 拉分支。

**验收不通过**：PR 置 `changes requested`，写清「缺哪条证据 / 哪条判据不符 / 需要什么」；不占新轮次，算同轮返工。
**验收方自己出错**（如判据引用错、误杀长跑）：记为验收方 finding，不计执行方账，并在报告里写明更正。

## 评分与等级

```
准确性 A = 100 × (PASS×1.0 + PARTIAL×0.5) / (应验数 − BLOCKED数)
           − 阻塞缺陷数×10 − 不稳定项数×5        （下限 0）
完整性 C = 100 × [0.6 × 任务卡需求交付率 + 0.4 × 边界场景覆盖率]
效率   E = 100 − (实际轮次 − 计划轮次)×15 − 返工需求数×10   （下限 0，上限 100）
一致性 K = 100 − 契约违规次数×25 − 文档未同步项×10          （下限 0）
综合 S   = 0.35A + 0.30C + 0.20E + 0.15K
```

| S | 等级 | 处置 |
| --- | --- | --- |
| ≥ 85 | 达标 | 归档，进入下一阶段规划 |
| 70 ~ 85 | 勉强达标 | 允许推进，挂账项与低分维度须在下一阶段首轮补齐 |
| < 70 | 不达标 | 冻结下游，出修正方案，重排执行路线 |

**单维红线**（不受总分保护）：`A < 70` → 一律不达标；`K < 75` → 强制契约复审，暂停并行。

**门结论**：全部 PASS 或 PARTIAL 且均非阻塞 + 契约级全绿 → 达标；PASS 率 ≥90% 且无 FAIL → 有条件达标；存在 FAIL 或 PASS 率 <90% 或契约级任一红 → 不达标。

## Common Rationalizations

| 借口 | 现实 |
| --- | --- |
| 「执行报告已经写了通过，我核对一下就行」 | 报告是待验证的声明，不是证据。验收的价值就在于独立重跑能推翻它——历史上多次如此。 |
| 「代码逻辑看着对，缺个证据应该不算 FAIL」 | 证据缺失一律 FAIL。「应该算对」和「算对」之间没有中间态。 |
| 「环境不支持，先按 PARTIAL 算过」 | 环境缺失是 BLOCKED，不计入分母，且不进结论列。挂账项要有明确的关闭时点。 |
| 「这个 finding 只是建议」 | 那就标 Optional/Nit，不要写成必改。标签含糊会让执行方要么全忽略、要么全返工。 |
| 「先记 PASS，等跑完再补证据」 | 结论宽于证据会让台账永久失真。**反过来写：先跑，再记。** |
| 「验收要点写得不对，我按代码实际行为判」 | 那是文档缺陷，提缺陷单走变更流程。执行者自解需求等于没有需求。 |
| 「差异是噪声，重跑一次就好了」 | 噪声有量级。先给数值（spread 135.6% vs 160%），再看是否落在判据带宽内。 |

## Red Flags

出现任一即判本轮验收流程失效：

- 采信执行报告结论而不重跑
- 结论列宽于证据（例：LT-01 实际 2/12 段却记 PASS）
- 覆盖模型默认「视为已实现」——漏写一节就自动算已交付
- finding 没有 remedy，或只写「这里太复杂，建议优化」
- 无严重度标签，必改与建议混在一起
- 用例读取共享目录里的旧产物，旧文件被误判为本轮结果
- 验收方改了 `verify/` 或 `src/`
- 为让测试通过而下调验收要点
- 只看总分不看维度，单维红线被平均掉
- 新断言未在旧代码上跑红就宣布通过
- 归档时不回写台账，下一轮失忆重复踩坑

## Verification

验收完成前逐项确认：

- [ ] 每条需求都有独立判定，且有可复现证据（命令 + 输出 + 时间戳）
- [ ] 所有需求级用例**由验收方独立跑过**，非引用报告
- [ ] 每个 finding 都有严重度 + 定位 + 复现 + **remedy**
- [ ] 契约级检查通过（构建绿、接口无未登记变更、依赖白名单、许可合规、文档同步）
- [ ] 门判据逐条对照，门结论已给出
- [ ] A/C/E/K 已计算，单维红线已检查
- [ ] `docs/07-执行台账.md` 已回写，结论列与实测一致
- [ ] `docs/09-V1.0覆盖表.md` 状态与实现一致
- [ ] 下一轮指令已产出，含验收标准与通过判据
- [ ] 每条问题已归因到 执行者 / 规划 / 环境
