# 五轴映射 · 严重度标签 · remedy 词表 · 归因

## 1. 五轴 ↔ 项目四维

| 轴 | 通用技能的关注点 | 本项目落点 | 产出 |
| --- | --- | --- | --- |
| **Correctness** | 是否符合需求、边界与错误路径、测试是否真在测对的东西 | 06 §6.1 四档判定（PASS/PARTIAL/FAIL/BLOCKED） | 逐项判定表 |
| **Readability & Simplicity** | 命名、控制流、多余抽象、**能否更少行数** | `code-simplification` 技能 | findings（Optional/Nit 为主） |
| **Architecture** | 是否沿用既有模式、文件域是否越界、**复杂度是减少还是搬家** | 06 §2 文件域白名单 + `CONTRACT.md` §2/§3 | findings（Required/Critical） |
| **Security** | 输入校验、敏感信息、依赖许可 | 06 §6.2 许可合规 + `security-and-hardening` | findings |
| **Performance** | 无界循环、同步阻塞、热路径大对象 | 05 性能判据 + `performance-optimization` | findings（Required） |

四维与轴的对应关系：

```
A（准确性 35%） ← Correctness 为主
C（完整性 30%） ← Correctness 的边界覆盖 + Architecture 的范围覆盖
E（效率  20%） ← 轮次与返工，反映流程损耗
K（一致性 15%） ← Architecture + Security（契约、依赖、文档）
```

## 2. 严重度标签

| 标签 | 判定标准 | 执行方动作 | 计入 |
| --- | --- | --- | --- |
| **Critical** | 安全漏洞、数据损坏、功能破坏、**结论列宽于证据**、改动越出文件域 | 必须修，且需重新验收 | A 扣分 + K 扣分 |
| *(无前缀)* / **Required** | 与需求不符、缺证据、契约违规、回归失败、边界未覆盖 | 合并前必须解决 | 按所属轴扣分 |
| **Optional** / **Consider** | 改进建议，不影响正确性 | 可不做，需给理由 | 不扣分 |
| **Nit** | 格式、命名偏好、注释风格 | 可忽略 | 不扣分 |
| **FYI** | 背景信息、后续可选方向 | 无动作 | 不扣分 |

> 标签的作用是让执行方知道**哪些必须做**。标签含糊的代价是双向的：全标必改 → 大量无意义返工；全标建议 → 真问题被忽略。

## 3. remedy 词表（结构动作）

finding 只描述问题 = 无效 finding。必须落到以下动作之一：

| 症状 | 正确 remedy |
| --- | --- |
| 同形条件分支重复出现 | 提成类型化模型或显式 dispatcher |
| 特性专用逻辑混进共享模块 | 移回拥有该概念的层，复用 canonical helper |
| 缺少类型边界，靠静默 fallback 兜底 | 把边界显式化，让下游分支消失 |
| 复杂度只是换了地方 | 删掉一层抽象，让分支整体消失 |
| 新 helper 与既有 helper 近似重复 | 复用既有 canonical helper，删副本 |
| 死代码 / 调试残留 / 注掉的块 | 列出后征询删除，不静默删 |
| 单文件已超千行 | 先抽 helper / 子组件 / 模块，再往上加 |
| 特性改动混着无关重构 | 拆成两个变更分别提交 |
| 错误路径未处理 | 补错误分支并给出可观测的失败信号 |

### 本项目特有的 remedy

| 症状 | remedy |
| --- | --- |
| 改动落在任务卡声明的文件域之外 | 回滚越界改动；若确有必要，走契约变更单，不私改 |
| 接口签名变更未登记 | 补契约变更单 + 更新 `CONTRACT.md` 对应章节，再验收 |
| 用例读取共享目录旧产物 | 用例开跑前自清理目标产物；本轮产物必须由本轮生成 |
| 覆盖表与实现状态不符 | 以实测为准修覆盖表；根因若是覆盖模型默认值偏乐观，一并修模型 |
| 台账结论宽于证据 | 结论列改回与实测一致（PARTIAL 就写 PARTIAL），并写明未完成原因 |

## 4. 归因规则

每条问题必须归到三方之一。**把规划失误记在执行者账上，会导致后续所有任务卡倾向于「多写多错」或「少写少错」。**

| 归属 | 判定信号 | 后果 |
| --- | --- | --- |
| **执行者** | 任务卡已列明、实现与要求不符、可用既有实现未用 | 返工计入效率分（10 分/条） |
| **规划** | 任务卡漏项、文件域重叠、依赖错判、验收要点缺失 | 记入 O0 修正，不计入执行者效率分 |
| **环境** | 缺机型、缺设备、缺素材、缺编译器、缺外部工具 | 判 BLOCKED，挂账，不计入分母 |

同一问题可有多个成因，但**主责只能有一个**，其余在备注里写明。

## 5. 评分计算细则

```
应验数 = 任务卡「需求范围」列出的需求条目数（子句级覆盖的项目按子句计）
分母   = 应验数 − BLOCKED数

准确性 A = 100 × (PASS×1.0 + PARTIAL×0.5) / 分母
           − 阻塞缺陷数×10 − 不稳定项数×5        （下限 0）

完整性 C = 100 × [0.6 × 任务卡需求交付率 + 0.4 × 边界场景覆盖率]
           边界场景 = 01 中标注的「边界/已知限制」+ 05 §6 的 ER 用例

效率   E = 100 − (实际轮次 − 计划轮次)×15 − 返工需求数×10   （下限 0，上限 100）
           计划轮次：简单任务 1，含硬件验证 2，跨厂商 3

一致性 K = 100 − 契约违规次数×25 − 文档未同步项×10          （下限 0）

综合 S   = 0.35A + 0.30C + 0.20E + 0.15K
```

### 单维红线

| 红线 | 处置 |
| --- | --- |
| `A < 70` | 无论总分多少，一律**不达标**。需求没做对，其他维度高分没有意义 |
| `K < 75` | 强制走契约复审，**暂停并行** |

### 效率分不奖励「快但错」

返工需求按 10 分/条扣，一个任务卡返工 5 条即扣 50 分，足以把总分拖进不达标区。评估报告里要写明哪些轮次是**执行者自己的实现缺陷**（容器格式、字节序这类），哪些是**测量工具缺陷**——后者不计执行者返工，但要单独立项修工具。

## 6. 门结论判定

| 结论 | 条件 | 后续 |
| --- | --- | --- |
| **达标** | 全部 PASS，或 PARTIAL 且均为非阻塞；契约级全绿 | 进入下一门 |
| **有条件达标** | PASS 率 ≥ 90%，无 FAIL；PARTIAL 项有明确补齐计划（≤ 1 轮） | 允许进入下一门，补齐项挂账追踪 |
| **不达标** | 存在 FAIL，或 PASS 率 < 90%，或契约级任一红 | 退回，出修正方案 |

> 「有条件达标」是防止流程僵化的缓冲阀，但**挂账项必须在下一次门关闭前清零**，否则自动升级为不达标。

## 7. 偏差分型（不达标时用）

| 偏差类型 | 判定信号 | 修正动作 | 是否重排 |
| --- | --- | --- | --- |
| **E1 证据缺失** | 代码可用但无 EVIDENCE | 退回补证据，不重做实现 | 否 |
| **E2 实现不符** | PASS 率低且集中在某模块 | 退回该角色修复，重跑验收 | 否 |
| **E3 契约破坏** | 接口被改 / 跨域写入 | 冻结下游 → 回滚或补变更单 → 全链路回归 | 是（下游全部重验） |
| **E4 上游能力不成立** | 硬编不可用、平台 API 不可用 | 触发**文档变更**，再重排依赖 | 是（结构性） |
| **E5 规划失误** | 任务卡漏项 / 文件域重叠 / 依赖错判 | 修任务卡 + 修依赖表 | 是（局部） |
| **E6 环境缺失** | 缺机型、缺设备、缺素材 | 判 BLOCKED，降级验证或推迟 | 否（挂账） |
| **E7 反复不通过** | 同一需求 3 轮 FAIL | 拆小任务卡 / 换实现路径 / 走需求降级变更 | 是 |

### 影响面清单（重排前必做，缺一不可）

| 清单 | 内容 | 用途 |
| --- | --- | --- |
| 受影响需求 | 直接失败的需求编号 + 依赖它的下游需求 | 确定回归范围 |
| 受影响交付物 | 接口、文件、配置、文档章节 | 是否需通知下游重接 |
| 受影响门 | 已通过但需复验的 Gate | 确定回退深度 |
| **不受影响项** | 明确列出「无需重验」的部分 | 防止过度回归拖慢节奏 |

**回退深度最小化**：能只重跑本门就不回退到上游；只有契约变更才回退到最深依赖点。
