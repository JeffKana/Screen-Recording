# 交付包规范：四件套 · 文件域 · 覆盖模型

> 任务卡目录：`tasks/{门}/{角色ID}-{序号}/`

## 1. 四件套

### 1.1 TASK.md（输入，只读）

规划侧写入，执行侧只读不改。缺失以下字段时退回规划侧：

| 字段 | 说明 |
| --- | --- |
| 需求范围 | 逐条列出的需求号 + 验收要点引用 + 证据形式要求，**不可增删** |
| 必读章节 | 01 / 02 / 03 / 05 中必读的章节号，缺一不可 |
| 文件域 | 声明可写目录，**白名单** |
| 上游交付 | 版本 / 分支 / 接口清单校验值 |
| 截止门 | 属于哪个 Gate |
| 约束 | 禁止项（禁改目录、禁引依赖、必须提供自测命令等） |
| 完成定义 | DoD |
| `## 覆盖子句` | 实际覆盖的子句清单（`M2-09#1` 形式） |
| `## 交付状态` | 三态之一：`已实现` / `有卡未实现` / `无卡` |

### 1.2 EVIDENCE.md（验收的唯一凭据）

```markdown
# EVIDENCE: {角色ID}-{序号}

> 口径声明: {例如「代理 ≠ LT-01，本轮未证明单文件 8 小时」}
> 数据来源: {时间戳} / {构建目录} / {机器}

## {需求号} {需求标题}
- 验证方式: {如何验证}
- 命令: `.\build\Release\xxx.exe --flag`
- 输出: artifacts/{文件名}.txt（{关键结论}）
- 结论: 通过 / 部分通过 / 不通过
- 复现环境: {机器} / {系统版本}
```

**证据格式的三条硬要求**：

1. **一个需求一条证据**——不允许「上面那条的验证也覆盖了这条」。
2. **必须含可重跑的命令**——不接受「手动点了一下」。
3. **输出必须可核验**——文件存在、日志含关键字、截图可见现象。验收方有权要求重跑。

**证据必须诚实标注未完成**。写「2/12 段完成，其余未跑」并给挂账，比写「PASS」再在别处补一句「未完成」更安全：后者是结论宽于证据，会让台账永久失真。

**数值型判据必须给实测值**。「偏差 ≤100ms」要写「实测 63ms」。「spread 135.6%」比「spread 偏高」有用一百倍——数字让验收方能判断是缺陷还是噪声。

### 1.3 SELFTEST.md（自测记录）

```markdown
# SELFTEST: {角色ID}-{序号}

## 0. 开工四项自查
| 检查项 | 结果 | 依据 |
| --- | --- | --- |

## 1. 自测命令与输出
| 命令 | 结果 | 时间戳 |
| --- | --- | --- |

## 2. 红-绿对照
| 新断言 | 旧实现实测 | 新实现实测 |
| --- | --- | --- |

## 3. 回归
| 用例 | 结果 |
| --- | --- |

## 4. DoD 勾选
- [ ] ...
```

### 1.4 HANDOFF.md（交接说明）

**必须回答四个问题，缺一项则门不通过**：

| 问题 | 示例 |
| --- | --- |
| 我改了什么接口？ | 「`ICaptureSource::Acquire` 增加 `out PTS` 参数」 |
| 下游需要接什么？ | 「S4 需按 PTS 单调写入，允许空洞」 |
| 已知限制是什么？ | 「UAC 提权窗口在黑屏时不发错误码，仅记 Warn 日志」 |
| **哪些需求我**没**做完？** | 「无」或「M1-10 未纳入本任务卡」 |

第四个问题最容易漏答，也最重要。它是下游规划与下一轮排期的输入。

### 1.5 artifacts/

截图、日志片段、成片样本。**>5MB 只存路径**，不要把大文件塞进交付包。命名带需求号，便于验收方定位：

```
artifacts/m1-07-windowlist.txt
artifacts/m1-09.mp4
artifacts/fail-20261023-175725-m3-04-cbr-spread/context.txt
```

## 2. 文件域白名单

| 规则 | 违规判定 |
| --- | --- |
| 只能写任务卡声明的目录 | 改动声明外文件 → 一致性分扣 25 |
| 不得修改 `tasks/` 下他人任务卡 | 直接判定该轮不达标 |
| **不得为了让测试通过而修改 `verify/` 下的用例** | 判定为严重违规，本轮作废 |
| 接口变更必须留契约变更单 | 未留单的接口变更 → 扣 25 并要求回滚 |
| 不得引入新三方依赖（`vcpkg.json` 只读） | 直接判定不达标 |

跨域确有必要时：**停工 → 提契约变更单 → 由规划侧决策**。不私改。

## 3. 覆盖模型

覆盖表（`docs/09-V1.0覆盖表.md`）的三态必须与实现一致：

| 状态 | 含义 |
| --- | --- |
| 已实现 | 有卡、有实现、有证据 |
| 有卡未实现 | 有卡，但实现缺失、仅引擎级达成、或产品入口缺失 |
| 无卡 | 未切片，必须逐条挂账（C8 校验项） |

### 已踩过的坑（别再踩）

| 坑 | 后果 | 正确做法 |
| --- | --- | --- |
| 任务卡正文「顺带提到」的需求号被算作覆盖 | 覆盖表虚高 | 只认 `## 覆盖子句` 节 |
| `## 交付状态` 写成非「已实现」的任意值仍被算作已覆盖 | 覆盖表虚高 | 非「已实现」的任意写法都按未实现处理 |
| 缺 `## 交付状态` 节的历史卡默认算「已实现」 | **漏写一节 = 自动算已交付** | 默认应是「有卡未实现」，要翻绿必须显式声明 |
| 覆盖模型默认偏乐观 | 洞永远靠人自觉 | 收紧默认值 + 历史卡补节 |

> 这四条是同一类问题的不同入口：**默认值偏乐观**。收紧默认值比靠人自觉可靠。

### 覆盖粒度

覆盖表已改为**子句级**（如 `M2-09#1`、`M2-09#2`）。任务卡必须用 `## 覆盖子句` 声明实际覆盖的子句，粒度不得粗于需求本身。

引擎级达成 ≠ 产品可交付。例：帧率引擎实测 59.1fps 达标，但设置面板没有帧率入口、用户选不了 → 仍是**有卡未实现**。
