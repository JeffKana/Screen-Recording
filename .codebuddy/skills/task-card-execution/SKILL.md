# 任务卡执行（Task Card Execution）

## Overview

执行侧只做一件事：**把任务卡上的需求变成带证据的交付包**。交付包由验收侧独立重跑判定，执行方无权自己写「通过」。

交付包结构（每张任务卡一份，位于 `tasks/{门}/{角色ID}-{序号}/`）：

| 文件 | 作用 | 缺失后果 |
| --- | --- | --- |
| `TASK.md` | 输入（规划侧写入，执行侧只读） | — |
| `EVIDENCE.md` | **验收的唯一凭据** | 无证据即 FAIL |
| `SELFTEST.md` | 自测命令与输出 | 门不通过 |
| `HANDOFF.md` | 交接说明（四个必答问题） | 门不通过 |
| `artifacts/` | 截图、日志片段、成片样本（>5MB 只存路径） | 可选 |

> **交付包不是「我做了什么」的说明，是「验收方能自己复现」的凭据。**

## When to Use

**使用**：拿到任务卡要开工；需要判断某条需求算不算做完；需要交出可验收的包。

**不使用**：
- 要切片、排期、决定下一轮做什么 → 那是规划侧
- 要判定交付是否合格 → 用 `acceptance-review`，**执行方不得自评**

## 开工四项自查（缺一不开工）

来自 06 §4.2。**任一项不通过，立即退回规划侧，不要自行解释，也不要先改了再说。**

| 检查项 | 通过标准 | 不通过的处理 |
| --- | --- | --- |
| **需求编号可检索** | 需求号能在 `../../../docs/01-功能需求清单.md` 查到原文 | 退回规划侧修正任务卡，**不得自行解释** |
| **必读章节可定位** | 任务卡列的章节在指定文档里存在、编号能定位 | 退回规划侧；文档缺章按文档缺陷处理 |
| **上游交付物可获取** | 上游版本/分支/接口清单能拿到 | 阻塞并上报，**不得用旧版本开工** |
| **文件域无交集** | 声明的文件域与当前并行任务不重叠 | 上报规划侧重排，禁止「先改了再说」 |

自查结果写进 `SELFTEST.md` 开头，让人一眼看到这轮是怎么开起来的。

## The Process

### Step 1 · 读卡并锁定范围

1. 读 `TASK.md`：需求范围、必读章节、文件域、截止门
2. 回 `../../../docs/01-功能需求清单.md` 读**验收要点原文**——任务卡里的是转述，原文才是判据
3. 读 `../../../CONTRACT.md` 相关章节（接口清单、错误码表、状态机转移表、门判据）
4. 读 `../../../docs/02-系统架构.md` 的数据流与接口契约

**锁定三件事**：要改哪些文件（白名单）、每条需求的验收要点原文、哪些接口不能动（动了要开契约变更单）。

### Step 2 · 装载上下文

按 `context-engineering` 的思路，只加载本轮需要的：
- 本轮要改的文件 + 它们的直接依赖
- 对应判据（01 的要点、05 的用例、CONTRACT 的条款）
- 已有的同类实现（复用，别重造）

**不要**把整个 `src/` 读一遍。上下文越复杂，越容易在无关文件上「顺手改」。

### Step 3 · 薄切片实现

按 `incremental-implementation` 的切片策略：
- 一个切片 = 一条需求 = 一组可验证的改动
- 每片独立可编译、可自测
- 改动规模控制在一次 review 能看完的量级（单文件别超千行）

**红线**：
- **不越文件域**。确需跨域 → 停工，开契约变更单
- **不引入新三方依赖**（`vcpkg.json` 只读）
- **不为了让测试通过而改 `verify/` 下的用例**——那是改尺子
- 不做与本任务无关的重构、清理、改名

### Step 4 · 先红后绿

按 `test-driven-development` 的 red-green-refactor：

```
1. 写断言 → 在【未修复】的产物/代码上跑，必须 FAIL（红）   ← 这一步不能省
2. 实现修复
3. 再跑 → PASS（绿）
4. 把旧值与新值都写进台账
```

**只在当前代码上跑绿的断言不算证据，只能标「回归护栏」。**

红-绿对照表是交付包的必备内容，格式：

| 新断言 | 旧实现实测 | 新实现实测 |
| --- | --- | --- |
| `auto-resume-self-exit` | 暂停→客户端退出后 8s 仍存活，无 `record_exit`、无成品 | 1505ms 自动恢复，`record_exit=0`，成品 5.999s |

### Step 5 · 交付前自检

按 Definition of Done 逐项过（Correctness + Quality 两节必过）：

- [ ] 任务卡每条需求都有对应证据
- [ ] 新增断言都先红后绿，旧值已记录
- [ ] Release + Debug 均编译通过，零告警
- [ ] 相关回归零失败（说明依据：全量 or 文件域抽样）
- [ ] 无死代码、无调试残留、无注掉的块
- [ ] 改动未超出文件域
- [ ] 接口若有变更 → 已开契约变更单 + 已更新 `CONTRACT.md`
- [ ] 文档已同步（README / 台账 / 覆盖表 / 任务卡 `## 交付状态`）

### Step 6 · 产出四件套

按 `references/delivery-contract.md` 的规范写 `EVIDENCE.md` / `SELFTEST.md` / `HANDOFF.md`。

三条最容易忽略、但直接导致 FAIL 的硬要求：

1. **一个需求一条证据**——不允许「上面那条的验证也覆盖了这条」
2. **必须含可重跑的命令**——不接受「手动点了一下」
3. **输出必须可核验**——文件存在、日志含关键字、截图可见现象。验收方有权要求重跑

## Common Rationalizations

| 借口 | 现实 |
| --- | --- |
| 「代码写完了，证据回头补」 | 证据回头就补不上。跑的时候顺手截、顺手存，比回头翻强十倍。 |
| 「这条需求跟另一条是同一个验证」 | 一需求一证据。共用证据等于两条都判不出来。 |
| 「这个断言在旧代码上也过，说明它不是回归护栏而已」 | 那它就没证明你修了什么。先红后绿是硬要求，不是加分项。 |
| 「顺手把这个文件重命名了，更清楚」 | 范围纪律。你改的每个文件都会被人 review，混入无关改动会让 diff 变难读、风险变大。 |
| 「这里逻辑太乱，我重构一下」 | 架构变更单独开任务卡。混在功能里做，回归范围失控。 |
| 「需求要点写错了，我按合理解释实现」 | 提文档缺陷单。自行解释 = 验收时按别人的理解判，你必挂。 |
| 「反正验收方会重跑，我这边跑不通也无所谓」 | 你这边跑不通，交上去就是 FAIL。 |
| 「覆盖表先写已实现，验收完了再改」 | 结论宽于证据会让台账失真。写「有卡未实现」不丢人，写假绿才丢人。 |

## Red Flags

出现任一即判交付包不合格：

- `EVIDENCE.md` 缺失，或某条需求无对应证据
- 证据里没有可重跑的命令（只有「已验证」「符合预期」）
- 新断言没有先红后绿记录
- 改动越出任务卡声明的文件域
- 修改了 `verify/` 下的用例
- 引入新依赖（`vcpkg.json` 被改）
- 接口签名变了但没开契约变更单、没更新 `CONTRACT.md`
- `HANDOFF.md` 四个问题有任何一个没答（尤其「哪些需求我**没**做完」）
- 任务卡缺 `## 交付状态` 节，或状态写成非「已实现」的任意值却被算作已覆盖
- 自己把交付标成「已验收」
- 顺带做了无关重构

## Verification

交付前逐项确认（勾选结果写进 `SELFTEST.md` 末尾）：

- [ ] 开工四项自查全部通过并已记录
- [ ] 任务卡每条需求 → 一条证据，含命令与输出
- [ ] 红-绿对照表完整（旧值 + 新值）
- [ ] Release + Debug 零告警
- [ ] 回归零失败，依据已说明
- [ ] 文件域无越界，`vcpkg.json` 未改，`verify/` 未改
- [ ] `HANDOFF.md` 四问齐答，含「哪些需求我没做完」
- [ ] 任务卡 `## 交付状态` 已写，且与实际一致
- [ ] `## 覆盖子句` 只列实际覆盖的子句（不靠正文顺带提及充数）
- [ ] 已知限制已写明（含「降级验证」标注）
