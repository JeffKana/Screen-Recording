## 2. M3-05 的实现边界（别做成"假列表"）

01 的原文是「界面显示**实际可用**列表」「不可用项不出现或标注**不可用原因**」。两种做法都合规：

- A：只列真正可用的（本机大概只有 `mf-h264-sw`），其余不显示；
- B：全列 + 原因（`NVENC 未检测到 NVIDIA 驱动 / QSV 需 oneVPL 运行时 / AMF 需驱动`）。

**推荐 B**，因为用户看不到"为什么没有硬编"就会去报 bug。但原因必须来自**真实探测**（`MFTEnumEx` 结果、`MFXLoad`/`nvEncodeAPI` 的 dll 是否存在），不能写死一句话。

验收要点：
1. 列表项数 ≥ 1，且 `mf-h264-sw` 必在其中；
2. 强行指定不可用编码器 → 启动失败并给出原因（复用现有 `exit 6` 路径）；
3. 日志 `encoders=[...]` 与 UI 列表逐项一致。

## 4. 注意事项

1. **改合并规则要配对抗用例**：只改代码不造"旧卡说已实现、新卡说没实现"的场景，等于没改。
2. 覆盖数字会**下降**（87→85），这期间 G5 已关闭、**不得**被解读为回归；在 `docs/09` 顶部加一行「2026-10-29 因 M3-05 声明纠偏，已实现 87→85」。
3. M3-05 的探测不要拖慢启动：`MFTEnumEx` 很快，但 `MFXLoad`/驱动查询可能慢，放在设置页首次打开时做，不放在录制启动路径上。
4. G6 的 zip 不要打包 `.pdb`、`verify/`、`docs/`；只带 exe + 必要 DLL + 许可声明。
5. 本轮**不要**重跑 8h；G5 已关闭，长录制只在 G6 的发布验证清单里跑一次即可。
