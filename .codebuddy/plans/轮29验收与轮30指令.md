## 3. 四个发现

**F1 · 覆盖表仍有"有卡 = 已覆盖"的洞：M8-14 实际没实现**

`docs/09` 把 `M8-14#1/#2` 标成"有卡"，引用 `tasks/G1/S1-002/TASK.md`。但那张卡自己写的是：

> `| M8-14 | 一键导出含版本、硬件、日志、配置的诊断包 | 骨架阶段先落 --version 与管道会话日志 |`

而 `src/` 下**没有 `diag/` 目录**（只有 app/audio/capture/compositor/core/encode/ipc/mux/platform/recorder/resilience/tools），也没有任何"导出诊断包"的入口。

也就是说：子句级拆分解决了"哪条子句"，没解决"卡是否真的交付了"。当前只有两态（有卡/无卡），缺了第三态——**有卡但未实现**。这一态不补，C8 永远绿，而 V1.0 会带着空洞发布。

修：`docs/09` 的「状态」列改成 `已实现 / 有卡未实现 / 无卡`；C8 对"有卡未实现"同样要求挂账。首批至少要回扫 G1 的两张卡（M8-14、M2-16 需确认）。

**F2 · 异常清理没系统化：只有 g4_gate 有 trap**

上一轮那次孤儿进程的根因（读日志共享冲突 → 脚本异常退出 → UI 没清理）修在了 `g4_gate.ps1` 一个文件里。我扫了一遍：

```
trap=1: g4_gate.ps1
trap=0: g1/g2/g3_output/g3_playback/g3_recovery/g3_storage/
        g4_channel/g4_control/g4_elapsed/g5_fallback/g5_inject/stimulus/ui_smoke
```

`ui_smoke.ps1` 恰恰是**启动 UI 进程最多的那个**，它只在开头（`:184`）和结尾（`:442`）清理，中途抛异常就没有兜底；而且它还有 3 处 `File.ReadAllText` 读 INI（`:394/402/425`），没有 try/catch——与上次出事的写法同类。

修：抽一个 `verify/lib/Cleanup.ps1`（注册进程 + trap 调用），所有 spawn 进程的脚本统一引用。这不是"再加一层保险"，是把**同一类问题一次修完**。

**F3 · 四个测试开关进了产品二进制**

`--preflight-fail`、`--set-region`、`--set-output`、`--set-hotkey` 都在 `sr-ui.exe` 里。自动化需要它们，但 G6 打安装包前应当用编译宏隔离（`SR_TEST_HOOKS`），或在 `--help` 里明确标「调试」。

**F4 · M6-06（150% DPI）仍是 BLOCKED**

代码走了 per-monitor v2 + `GetDpiForWindow` + 物理像素，100% 下选区与成片一致；150% 需要真机。轮 29 没有把它标 PASS，这个处理是对的。**继续保持**，直到有设备。

## 4. 轮 30 指令（T-17 可观测 + 覆盖表收口）

### 目标
把"录制中发生了什么"变成可查：三项实时指标 + 一键诊断包；同时把覆盖表的第三态补上，让 C8 真正有意义。

### 范围与优先级

| 优先 | 项 | 具体要求 | 验收标准 |
| --- | --- | --- | --- |
| **P0** | M6-03 三项指标 | 采集 fps、编码 fps、丢帧数；录制中实时可见（状态栏/悬浮条 + 日志） | 指标每秒刷新；人为丢帧后计数增加且日志有对应记录；数值来自 recorder 真实计数，UI 不推算 |
| **P0** | M8-14 诊断包 | 一键导出目录：版本、GPU/显示器、最近 10 分钟日志、配置快照 | 导出目录含上述四类；**不含任何画面/音频内容**（grep 断言无 png/jpg/mkv/帧数据）；大小 <5MB；导出 ≤2s |
| **P0** | 日志分级 | `--log-level debug/info/warn` + INI，默认 info | 切到 debug 后多出调试行；warn 下只剩异常；分级在运行中可切（或重启生效，二者取一并写清） |
| **P1** | 覆盖表第三态 | 状态列改 `已实现 / 有卡未实现 / 无卡`；C8 覆盖三态 | 回扫 G1 两张卡；M8-14 在本轮后转"已实现"；C8 仍 8/8 |
| **P1** | 脚本清理统一 | `verify/lib/Cleanup.ps1` + 所有 spawn 脚本接 trap | 任一脚本中途抛异常后，`sr-ui`/`sr-recorder` 残留 = 0（可人为制造一次异常验证） |
| **P1** | 测试开关隔离 | `--*-fail/--set-*` 走编译宏或标调试 | Release 包 `--help` 里能看到标注；不影响现有自动化 |

### 验收标准

**自动化（计入 PASS）**
1. `g5_diag.ps1`（新）：录制中三项指标 3 次采样递增合理；注入丢帧 → `dropped>0` 且日志有 `dropped=` 行；
2. 诊断包：导出 → 校验存在 `version.txt` / `gpu.txt` / `log.txt` / `config.ini`；断言目录内无图片/视频；总大小 <5MB；
3. 日志分级：debug 行数 > info 行数 > warn 行数；
4. 全部回归：`g4_gate` 12、`ui_smoke` 101、`g4_elapsed` 13、`g4_channel` 52、`g4_control` 32、`g5_*`、`g3_*`、`g1` 40、`g2` 18、契约 8/8、覆盖表 up to date。

**人工（单列）**
- 状态栏/悬浮条的指标排版、诊断包导出对话框 —— 截图。

### 注意事项

1. **指标必须来自 recorder**，不要在 UI 侧用"帧数/时间"倒推——那又是一次自证。recorder 已有 `frames_encoded`/`frames_duplicated`，缺的是"采集侧到达帧率"和"编码侧出包帧率"，各加一个每秒滑窗计数即可。
2. **协议扩展沿用 kind 的方式**：`StateSnapshotPayload` 尾部追加字段，旧客户端读已知字段即可（`Reader::Remaining()` 判断），不改 §7 帧格式、不升版本。但这已经是第二次追加，建议这次加一个 `payload_len` 自描述或直接排一个 v2 计划，别每轮加一字节。
3. **诊断包绝不能含画面**（05 ER-14）。日志里也不要有窗口标题、文件名以外的用户内容——导出前扫一遍日志，把路径里的用户名脱敏。
4. 日志"最近 10 分钟"要用环形缓冲，不要整文件拷贝：8h 录制的日志可能有几十 MB。
5. drain 优化（崩溃丢失 3s→2s）本轮**不做**，它是优化不是需求；等 G5 代理测完再决定值不值。

### 通过判据
`g5_diag` 全绿 + 诊断包内容与"无画面"断言通过 + 全部回归零失败 + 契约 8/8（含新三态 C8）+ 双构建零告警 + 无残留进程。
