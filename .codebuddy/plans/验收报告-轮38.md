## 2. M1-08：「硬阻塞①」不成立

执行报告的原文是「本机 SDK 没有缩放 API，`ID3D11VideoContext` 没有 `VideoProcessorSetStreamScaling`，`d3d11video.h` 不在 SDK 里」。

但同一份代码里：

```304:315:src/compositor/Nv12Converter.cpp
    // 本机 SDK（10.0.26100）的 ID3D11VideoContext 没有 VideoProcessorSetStreamScaling，
    // VideoProcessor 只能 1:1 搬运：源尺寸 ≠ 输出尺寸时不能走 GPU（会 Blt 失败）。
    D3D11_TEXTURE2D_DESC source_desc{};
    source->GetDesc(&source_desc);
    if (source_desc.Width != width_ || source_desc.Height != height_) {
        ...
        return false;      // ← 自己拦死
    }
```

```341:344:src/compositor/Nv12Converter.cpp
    video_context_->VideoProcessorSetStreamFrameFormat(...);
    video_context_->VideoProcessorSetStreamSourceRect(processor_.Get(), 0, TRUE, &source_rect);
    video_context_->VideoProcessorSetStreamDestRect(processor_.Get(), 0, TRUE, &dest_rect);
```

`VideoProcessorSetStreamDestRect` **就是**缩放 API，而且**代码已经在调用它**（能编译、1:1 时能跑通）。`VideoProcessorSetStreamScaling` 这个函数在 D3D11 里从来没存在过——他们在找一个不存在的名字，然后得出了"SDK 没有"。

真实机制几乎可以确定是：`VideoProcessorEnumerator` 与 `VideoProcessor` 在创建时绑定了 `D3D11_VIDEO_PROCESSOR_CONTENT_DESC` 的 InputWidth/InputHeight，**源尺寸变了必须重建 processor/enumerator**，否则 Blt 失败。这也是为什么"1:1 能过、变了就失败"，跟缩放能力无关。

**这直接改变结论**：M1-08 不是环境阻塞，是"该重建的没重建 + 有一道自设护栏挡着"。按 Skill 的定义，环境缺失才叫 BLOCKED；这里只能判 **FAIL（未交付）**。

## 3. 崩溃：真缺陷，但不能靠"关掉机制"绕过

第二条阻塞（重建采集源后 0xC0000005，5 次 2 次）我认可它是真的，而且从代码能看到生命周期隐患：

```946:955:src/recorder/RecordingSession.cpp
            } else if (source->NeedsRebuild()) {
                source->Stop();
                if (!source->Start(request, rebuild_error)) { ... }
                have_frame = false;     // ← 只清标志，latest 仍指着已销毁 pool 的裸指针
            }
```

`latest.native_texture` 是裸指针，Stop 之后没有失效；WGC 的 frame pool 重建与上一帧引用之间存在竞态。

但更关键的是：**如果第 2 节成立（只需重建转换器），这条崩溃路径可能根本不需要走**——窗口尺寸变化时，WGC 是否必须重建 pool，取决于后端实现；先用最小实验分开验证，再决定修哪里。直接关掉机制等于放弃一个 V1.0 需求。

## 5. findings

**F1 [Critical] M1-08 的"SDK 无缩放 API"是误诊，且代码里有自设护栏**
- 定位：`src/compositor/Nv12Converter.cpp:304-315`（guard）与 `:343-344`（已在用 SetStreamDestRect）
- 现象：注释引用不存在的 `VideoProcessorSetStreamScaling`；尺寸不等时在 `:309` 提前 return，缩放分支永远走不到
- 复现：读码即可；`g5_window` 的 4 条 M1-08 断言因此永远 SKIP
- remedy：删掉 `:309` 的尺寸护栏；尺寸变化时**重建 enumerator + processor**（不是重建采集源），保留现有 dest_rect 计算；再测 800×600→1280×720
- 归属：执行者

**F2 [Required] 重建路径的生命周期隐患**
- 定位：`RecordingSession.cpp:946-955`
- 现象：`latest` 未失效；WGC pool 重建与上一帧裸指针引用竞态 → 0xC0000005（5 次 2 次）
- remedy：`Stop()` 后立即 `latest = {}` + `have_frame = false`；帧纹理用 ComPtr 持有到消费完；加 20 次连续 resize 的稳定性用例
- 归属：执行者

**F3 [Required] "机制已关闭且不留死代码"与代码不符**
- 现象：`:319-344` 的 fill/stretch 缩放分支被 `:309` 挡成不可达
- remedy：按 F1 修复后它自然活过来；在那之前不要在 HANDOFF 写"无死代码"
- 归属：执行者

**F4 [Nit] SKIP 理由的措辞**
- 现象：SKIP 写的是"复现访问冲突，未交付"，这是对的；但 HANDOFF 里把它归到"本机 SDK 限制"，会误导下一轮
- remedy：按 F1/F2 更正归因后再写
