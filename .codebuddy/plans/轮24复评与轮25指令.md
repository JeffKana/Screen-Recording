## 2. 核心发现：控制通道绕过了握手，`srctl` 用不了

CONTRACT §7 明确写着：

> 握手 | 客户端先发 `Hello{token}`，服务端校验 token 后回 `HelloAck{protocolVersion, processId}`；校验失败的服务端立即断开

但 `poll_control`（`RecordingSession.cpp:400`）对非 `Command` 消息直接 `continue`——**Hello 被丢弃，不回 HelloAck**。而 `srctl` 的流程是先发 Hello、**阻塞等** HelloAck。

我做了实测：

```powershell
# 录制中（--control-pipe 1），用现成的 srctl 发 pause
srctl --pipe \\.\pipe\sr.recorder.<pid> pause
→ srctl_hung=True          （2.5s 内未退出，被强杀）
→ 录制侧: paused_ms=0, control=lost
```

后果有三层：

1. **唯一现成的客户端不可用**：任何走握手协议的调用方（包括将来的 UI）都会卡在等 HelloAck。
2. **用例只能另造客户端**：`g4_channel.ps1` 自己拼帧、跳过握手，这违反了我给的硬边界「新用例必须复用 `srctl`，不得另造协议」——所以 14/14 证明的是「自定义客户端可用」，不是「控制通道可用」。
3. **本地任意进程可发 Stop**：没有 token 校验，`\\.\pipe\sr.recorder.<pid>` 谁都能连上去停别人的录制。

CONTRACT 现在自相矛盾：§7 说必须握手，§18.3 又把控制通道七条判据全标 PASS。

## 3. 另外三个缺口

**F1 · Stop 命令没有用例**（我到 P0-3 的第 2 条）
代码有 `stop_requested` 分支（`:419`），但 14 条断言里没有一条发 Stop。「UI 点停止」是最高频的操作，反而没测。

**F2 · 半帧只测了「短头」，没测「头齐 payload 不齐」**
`g4_channel` 的 F 组发 6 字节（不足 12），命中的是 `:127` 那条分支。真正危险的是「12 字节头已到、payload 未到」——命中 `:145`。实现是对的，但这条分支零覆盖。字节模式管道确实会把一个 13 字节的帧拆成 12+1，所以这不是假想。

**F3 · P1-2 的 E 用例测的不是它宣称的分支**
用例 D 段预置 8 字节垃圾 `.part`，然后 `--fail-write-after 1`。第 1 次物理写就是 Segment 头，`muxer.Open` 直接失败 → **exit 7**，`RepairIntoFallback` 根本没被调用。
断言写成 `record_exit -ne 0` 兜住了，但它验证的是「封装打不开」，不是「`.part` 不可修复 → 兜底失败 → exit 15」。这是第 4 次「用例测的和宣称的不一致」（D-27 / fail-encoder / D-31 / 这次）。

**该记的正面**：`FreePath` 的收敛是这轮真正的技术进步——一处实现、全占即失败、三处调用点统一；D-34 的修复带哨兵实测；`ClientSeen()` 把 absent/lost 分开报，也是对的做法。

## 5. 轮 25 指令（控制通道收口，1 轮）

**先回答你的问题**：现在开始，但轮 25 **不是 T-17**，而是把控制通道收口。T-17 顺延轮 26。
理由：你自己说过「它是唯一挡在 UI 前面的东西」——而它现在挡在**任何走协议的客户端**前面，T-09 接入必挂。先把这 20 行补完，T-17 才有意义。

### P0-1 握手（关本轮唯一硬缺口）
- 控制通道实现 CONTRACT §7：收 `Hello{token}` → 校验（`--token`，默认 `dev`）→ 回 `HelloAck{protocolVersion, processId, state}` + 一帧 `StateSnapshot`；失败立即断开。
- 之后才接受 `Command`；未握手的 `Command` 一律断开。
- 断言：`srctl pause` / `resume` / `stop` 三条命令端到端生效（**必须用 srctl，不得自造客户端**）；错误 token → 连接被拒、录制不受影响。

### P0-2 Stop 命令
`srctl stop` → 提前收尾、`exit=0`、成品可播、时长 < 设定值、`state_sequence` 走到 `Stopping,Idle`。
断言还要覆盖「暂停中 Stop」（`Paused → Stopping`）。

### P0-3 半帧的 payload 拆分
把同一帧按 **12 字节头 / 1 字节 payload** 分两次写：第一次 `TryReceive` 必须返回 false 且不消费；补齐后恰好解析 1 条。
（现有「6 字节短头」用例保留，两条一起覆盖 `:127` 与 `:145`。）

### P0-4 兜底失败分支（重做 P1-2 的 E）
- 新增诊断子命令 `--fallback-commit <part> --fallback-dir <dir>`，直接走与录制中相同的 `RepairIntoFallback`；
- 用 8 字节垃圾 `.part` 调用 → 断言 `exit=15`、兜底目录 0 文件、原 `.part` 保留、`error` 含 `fallback:`。
（这样测的是 `Probe → 不可修复 → 返回失败` 这条真分支，而不是「封装打不开」。）

### P1 文档与契约一致性
- CONTRACT §7 与 §18.3 对齐：要么补一句「录制模式控制通道同样执行 §7 握手」，要么走变更单说明豁免。**二选一，不能两处并存**。
- `--control-pipe <value>` 的取值目前被忽略（名字恒为 `sr.recorder.<pid>`）。要么改成无参开关，要么真的用这个值做管道名——现在这样写 `--control-pipe 1` 会误导调用方。
- 08 §18 与台账补记本轮结果与上述缺口。

### 通过判据
`g4_channel` ≥ 22 条全绿（含 srctl 三条命令 + payload 拆分 + stop）；`g5_fallback` ≥ 26 条；`g4_control` 32、`g5_inject` 28、`g3_*` 15/11/9；契约 7/7；MSVC + MinGW 零告警。

### 硬边界
1. 用例必须用 `srctl`，不得再自造协议客户端（本轮已经破例一次）。
2. 握手不得改线格式（`Hello`/`HelloAck` 早已在 CONTRACT §7 定义，直接用）。
3. 未握手的连接必须断开，不得「宽容处理」。
