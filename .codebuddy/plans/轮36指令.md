## 2. R1 的具体做法（避免又变成"余量运气"）

1. 主循环结束后、`Close` 之前，计算 `expected_samples = media_elapsed_100ns / 10^7 * sample_rate`；
2. `while (audio_cursor < expected_samples - 1 block)` 继续 `Pull` 并写盘，最多补满 200ms；
3. 补不齐（采集已停）就把差值补静音，保证音轨不短于视频；
4. 断言写死：`duration - audio_end ≤ 100ms` **且** `≤ 3 × 内部点最大偏差`。

> 不要改判据阈值来迁就实现，需求就是 ≤100ms；现在是靠 1ms 的运气过，必须变成"结构上不会超"。

## 3. R2 的判据落地

```powershell
# ① 解码零错误（落盘端不参与判定）

# ③ 默认 vsync 的 [null] non-monotonically 警告不计，注释说明原因（D-58 同类：先怀疑尺子）
```

## 5. 注意事项

1. **R1 属于产品行为改动**（音频多写一点），要确认不影响：① 暂停/恢复的中断点；② `.part` 恢复后的时长；③ CBR/VBR 的音频码率统计。至少回归 `g4_control`、`g3_recovery`。
2. 重跑 8h 只在**必须**时做：R1 改动会影响尾部 100ms，若无法用 60s/10min 变长录制验证，再做一次 8h；否则以 60s + 10min 两级验证 + 理论补算代替，并在报告里写明「未重跑 8h 的理由」。
3. G6 的安装包不要引三方工具链；zip + 安装脚本 或 MSI 均可，先出方案再动手。
4. 收口阶段每轮只做 5 条子句，宁少勿多——上一轮一次做 4 条的节奏是对的。
