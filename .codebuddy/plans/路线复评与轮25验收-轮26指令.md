# 二、实现路线与阶段规划的合理性

## 2.1 判断

底座选型与分层是合理的，不需要推翻。**不合理的是任务排序**：连续 13 个任务（T-05 之后）没有一条 V1.0 的 UI 需求进入实现，G4 从 G3.5 时代就挂着，至今 12 个任务轮次。

根因不是执行慢，而是 **T-09 依赖 Qt6，而 Qt6 一直没装**。这个阻塞被记录成"外部阻塞"，然后每一轮都绕过它继续做后端——后端的边际收益已经很低了：控制通道解决的是"UI 怎么指挥录制"，而 UI 本身不存在。

## 2.2 五个具体偏差

**B1 · 门被拆成"半个门"推进。** G4 判据是「托盘/热键/倒计时/暂停恢复全链路」，倒计时与暂停恢复在 T-15/T-17a 做完了，托盘/热键为零。门定义与任务切片没对齐，于是"G4 快好了"变成一种错觉。

**B2 · 技术选型没有随版本重新评估。** 03 选 Qt6 是为 V1.5 的编辑时间轴考虑；但 V1.0 的 UI 清单只有 12 条，全是系统级控件（托盘图标、全局热键、置顶悬浮条、设置页）。用 Qt6 做这些，成本（在线账号安装 + vcpkg 变更 + 打包体积 40MB+）远高于收益。
08 §6 早就写了回退预案「Qt6 无法安装 → Win32 原生 + 托盘」，但这个回退从未被正式触发，一直以"阻塞"状态挂着。

**B3 · 验收脚本的可信度反复失守。** 同类问题已出现 5 次：D-27（采样到不存在的文件）、fail-encoder（断言匹配注入自造的字符串）、D-31（阈值未按轮重算）、P1-2E（测的是"封装打不开"却宣称"part 不可修复"）、轮 24（用例自造协议客户端绕过握手，把"通道可用"演成"自定义客户端可用"）。
这不是偶发，是缺一条硬规则：**新写的断言必须先在旧代码上跑成 FAIL**。红-绿一次，能挡掉上面五次里的四次。

**B4 · 阻塞项缺少"到期处置"。** LT-01 暂缓、Qt6 缺失、厂商 SDK 缺失，三项都以"挂账"存在，没有决策期限。挂账的本质是延期决策，拖久了会变成"永久不做"。

**B5 · 文档与实现出现双向漂移。** 08 §4 的任务表仍是"待开工"（靠 §8 的覆盖说明兜着）；32 条需求无卡；07 台账格式被空行切碎过一次。文档作为唯一事实源，这一条一旦松，评估就失去基准。

## 2.3 建议的路线调整（三条）

**R1 · UI 路线本周内决策，建议启用 Win32 回退。**
- 判据：若 Qt6 能在 1 天内装好且不影响契约（vcpkg 变更需 O0 批），继续 Qt6；
- 否则正式启用 08 §6 预案：`Shell_NotifyIcon` + `RegisterHotKey` + 自绘置顶条 + Win32 设置页（对话框）。
- 我的建议是后者：V1.0 只需托盘/热键/悬浮条/设置四项，Win32 原生 3 轮可出；Qt6 留到 V1.5 编辑时间轴再引。**这是按版本需要选技术，不是降级。**

**R2 · 一次性把 32 条未切片需求并入任务池**，按域分给 S1/S2/S5/S6，并在 08 建一张「V1.0 覆盖表」（66 行，逐条标 实现/任务卡/证据）。没有这张表，G0 的"需求可检索"永远只是形式。

**R3 · 验收硬化两条**：
1. 新断言必须红-绿（先在旧代码上 FAIL，再在新代码上 PASS），并在 SELFTEST 里留两行输出；
2. `contract_check` 增补 C8：V1.0 未切片清单必须为空，或每条都有挂账理由；C2 增加作者域校验。

## 3.3 未通过项（本轮不能判"通过"）

**N-1 · 阻塞级：手动暂停中控制通道断开 → 进程永久挂死（D-36）**

实测构造：`--seconds 10 --control-pipe`，1s 处连客户端发 `Pause`，随后客户端退出。

```
[record] control channel lost, recording continues
[record] control client reconnected
[record] paused at frame 105
[record] control channel lost, recording continues     ← 此后没有任何输出
```

40s 后进程仍存活（PID 36396，需强杀），**没有 `record_exit`、没有成品、`.part` 停在半截**。

根因：暂停等待循环

```cpp
while (!control_resume_pending && !stop_requested) {
    poll_control();
    Sleep(5);
}
```

`control_connection` 被 reset 后 `poll_control` 直接 return，两个标志**永远不会被置位**，也没有超时兜底。

影响：UI 崩溃、被任务管理器结束、或用户关掉 UI 时若正处于暂停，录制进程变成僵尸——用户以为在录，磁盘上什么都没有。按 05 §7.1 这是 **Blocker（录制无法完成）**。

修法（三选一，建议 1+2）：
1. 检测到 `control=lost` 且处于手动暂停 → 自动恢复录制并记 `pause_auto_resumed=1`；
2. 加暂停上限 `--pause-timeout`（默认 15 分钟），超时安全收尾并落盘；
3. 无论何时，控制通道断开都不能让主循环进入无退出条件的等待。

**N-2 · 一般级（风险，未复现）：重连握手在主循环内最多阻塞 1s**

`control_handshake` 的 1s 等待循环在 reconnect 路径上是从 `poll_control` 里调用的（`:446`）。一旦 accept 命中一个"连上但不发 Hello"的客户端，主循环会停 1s，约 30 帧。

我两次构造（静默客户端）都没有观察到 wall 变长（6.03s），所以**不算已证缺陷**；但代码路径存在，且违反"主循环永不阻塞"的口径。建议改成"每次只收一帧 Hello，收不到就下帧再看"，把 1s 等待从主循环里彻底移走。

# 四、轮 26 执行指令

## 4.1 目标
关掉 D-36（阻塞），把控制面的边界补全，冻结控制通道。**不进入 T-17。**

## 4.2 范围与优先级

| 优先 | 项 | 范围 | 验收标准 |
| --- | --- | --- | --- |
| **P0** | D-36 修复 | `control=lost` 且处于手动暂停 → 自动恢复（或超时收尾），不得无退出条件等待 | 新增用例：暂停 → 客户端退出 → 录制在 ≤2s 内自动恢复并正常收尾；`pause_auto_resumed=1`；成品可播；**进程必须自行退出** |
| **P0** | 暂停上限兜底 | `--pause-timeout <秒>`，默认 900 | 注入 3s 超时：暂停 3s 后自动恢复并记 `pause_timeout_hit=1`；成品时长 = 内容时长 |
| **P0** | 静默客户端不阻塞 | 握手改为"每帧最多收一帧"，1s 窗口从主循环移除 | 连上不发 Hello：`wall_seconds` 与不带客户端时差 ≤0.2s；`control=rejected` |
| **P1** | 重连后状态一致 | 重连时补一帧当前 StateSnapshot | 重连后客户端拿到的 `state` 与 `state_sequence` 末态一致 |
| **P1** | 边界用例补齐 | 暂停中断开 / 静默客户端 / 握手超时 / 重连后命令 | `g4_channel` ≥ 30 条 |
| **P1** | 文档 | 07 台账 + 08 §20；`D-36` 进缺陷明细 | 台账连续、按序 |

## 4.3 硬边界

1. **不得引入线程**、不得改成 OVERLAPPED；仍用 `PeekNamedPipe` 语义。
2. 修复必须保留"控制通道断开后录制继续"的既有行为（`g4_channel` E 组不得回归）。
3. 自动恢复的语义写进 CONTRACT §18.3，与"暂停不计时长"不冲突：自动恢复后**暂停时长仍不计入成片**。
4. 新增断言必须红-绿：先在本轮改动前的二进制上跑出 FAIL，再在改动后跑出 PASS，两行输出进 SELFTEST。

## 4.5 注意事项

1. **别用"给等待循环加个 Sleep 上限"了事**——先想清楚"谁该负责恢复"：控制通道是客户端，客户端消失时产品应自动恢复，而不是继续等一个不会再来的命令。
2. 自动恢复后如果用户重新连上并再次 Pause，要能正常工作（别把 `manual_pause` 做成一次性标志）。
3. 本轮结束后，`g4_channel` 应是**最后一个**在无 UI 情况下新增的用例；轮 27 起转观测与 UI。

# 五、给下一阶段的一句话

底座已经能稳定产出可播文件，异常路径也补到了「写失败能兜底、断电后能修复」的程度。
**剩下的 60% 工作量在 UI 与长录制上，而不在录制内核**——如果继续在这个内核上加功能，收益会迅速递减。
路线决策（R1）比任何一个后续任务都重要：**先定 UI 技术栈，再排期，否则 G4/G6 会一直"快好了"。**
