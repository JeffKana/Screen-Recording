## 2. DEFECT-02 裁定：**PASS**，但判据要改

**事实复核（我自己跑的）**

| 检查 | 结果 |
| --- | --- |
| stderr 构成 | 6,667 条，全部是 `[null @ ...] Application provided invalid, non monotonically increasing dts to muxer in stream 0: X >= X`（**相等**，不是倒序） |
| 同一窗口 `-vsync 0` 解码 | **0 条警告**（15990+700s） |
| 同一窗口默认 vsync 解码 | **6,667 条**（完整复现） |
| 包级 DTS | `15990~16700`：21,359 包，dup=0、backwards=0；`0~240`、`28600~28800` 同样 0/0 |
| 容器 | 22,374,134,176 B，与 manifest 一致 |

**结论**：文件本身时间戳严格递增、解码无 h264 错误；警告来自 **null muxer 的 CFR 帧率转换**（默认 `-vsync cfr` 把平均 33.35ms 的帧流按 1/30 取整，边界处产生重复 DTS）。把 vsync 关掉即 0 条，这是决定性反证。

**裁定（写入 `docs/05` M6-09 判据注释，不改需求原文）**

> 「完整可播」的判定三件套：
> ① `ffmpeg -v error -i F -f null -vsync 0 -` 退出码 0，且 stderr 无 `error` / `invalid data`；
> ② `-f framecrc` 的帧数 = `frames_encoded`，且 DTS 严格递增、无倒退；
> ③ **默认 vsync 下的 `[null @ ...] non monotonically increasing dts to muxer` 不计**——属落盘端行为，不是文件缺陷。

> 采样说明：全片 8h 逐帧解码成本高，我按其报告的唯一异常窗口（16,000~16,667s）做了 700s 完整 `-vsync 0` 解码 + 三处包级 DTS 校验；G6 发布前必须补一次全片解码（用新判据）。

## 4. findings

**R1 [Required] 终端音画偏差靠"余量"通过，机制上界 >100ms**
- 定位：`RecordingSession` 收尾段（最后一次 audio pull 之后即 Close）
- 现象：结尾点 v=28799.971 / a=28799.872 → **99ms**，判据 100ms，只差 1ms；15 个内部点均 0~26ms，说明不是累积漂移，是**尾部未补齐**
- 机制：每轮循环最多拉 8 块 × 1024/44100 ≈ **186ms**，尾部残量落在 0~186ms 区间；本轮抽到 99ms 属侥幸，重跑完全可能 120ms → FAIL
- remedy：收尾前按 `media_elapsed` 把音频补拉到对应样本数（最多 1 次额外 pull 循环）；用例加更严护栏「终端偏差 ≤3 帧(100ms) 且 ≤ 内部点最大值的 3 倍」
- 归属：执行者

**R2 [Required] DEFECT-02 的判据实现尚未按裁定改**
- 定位：`g5_lt01_real.ps1` 的全片解码段
- 现象：当前仍是「stderr 非空即 FAIL」，因此 8h 的 `full_decode` 被记成 FAIL、`summary.pass=8/fail=1`
- remedy：改成三件套（`-vsync 0` + framecrc DTS 递增 + 帧数比对），并把本次 6,667 条警告的定性写进用例注释
- 归属：执行者

**R3 [Nit] `summary.drift_points` 只有 15 点**
- 现象：数组从 1800 到 27000，第 16 点（28800）只体现在 `worst_drift_ms` 里，没有明细
- remedy：把结尾点也放进数组，便于复算
- 归属：执行者

**R4 [FYI] 目录枚举缓存第三次坑到我**
- 现象：`Get-ChildItem` 首读 `.part` 138MB，2 秒后 14.86GB（前两次同）
- remedy：判断写入用日志 mtime + 采样；这条已经写进我的验收习惯
