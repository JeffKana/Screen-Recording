## 0. 项目快照

### 0.1 目标与交付边界

本地优先的 Windows 桌面录屏工具，三句话目标：一键开录、录制稳定（8h 不崩不涨内存、异常中断可播）、导出即用（停止即得可分享文件）。

### 1.3 五个待修问题

**F1 · 收尾仍存在静默覆盖窗口（真实缺陷，D-24）**

MSVC STL 的 `std::filesystem::rename` 用 `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING)`（证据：`MSVC/14.44.35207/crt/src/stl/filesystem.cpp:722`）。
因此 `CommitOutput` 的第一段：

```88:95:src/recorder/OutputPath.cpp
    std::filesystem::rename(plan.part_path, plan.final_path, ec);
    if (!ec) { ... return true; }
```

在"目标已存在且未被独占"时**会直接覆盖成功**，不会走 `_001` 回退。D-23 只被修掉了一半：准备阶段避让覆盖了"开录前就存在"，**"录制期间被别人创建"这个窗口仍然是覆盖**。这正是 ER-07「原文件未被破坏」想排除的情况。

修法（6 行，不必改架构）：`CommitOutput` 在 rename 之前先做一次存在性避让（复用 `WithIndex`），再 rename；rename 失败仍保留现有重试。

**F2 · 写失败没有传播（T-16 的前置）**

```228:228:src/recorder/RecordingSession.cpp
            muxer.WriteVideo(packet.data, packet.size, packet.pts.value, keyframe);
```

返回值被丢弃（`WriteAudio` 同样）。磁盘写满/权限收回时，`WriteRaw` 返回 false，但会话继续"录"，最终要么 `Close` 报错返回 10、要么产出一个静默截断的文件。这意味着 T-16 的 ER-01/ER-04 现在**跑不出可信结论**——很可能出现"文件存在、结构合法、就是短了一截"的假 PASS。

顺带说明：**M8-06 后半的成本估计偏重了。** 01 写的是"录制中权限被收回时**停止并保存**到备用路径"，不是"重建封装续写会话"。检测到写失败 → 安全收尾 → `CommitOutput` 到备用目录，就能满足原文，不需要中途换封装。所以留给 T-16 是对的，但别按"续写"估工作量。

**F3 · 用例 B 没测到它宣称的机制**

B 步骤执行时 `same.mkv`、`same_001.mkv` 都已存在，`PrepareOutputPath` 直接给了 `same_002.mkv`，**`CommitOutput` 的重试分支一次都没进**。所以这条断言的真实含义是"准备阶段避让可用"，不是"M8-07 收尾换名可用"。另外 ER-07 要求的"原文件未被破坏"没有断言。

**F4 · 序号边界 off-by-one（轻微）**

```67:71:src/recorder/OutputPath.cpp
    for (int index = 1; index <= 999 && std::filesystem::exists(candidate, ec); ++index) {
        candidate = WithIndex(target, index);
        renamed = true;
        ec.clear();
    }
```

条件检查的是**上一轮的** candidate。若 `_001`~`_999` 全部存在，循环在 index=1000 时退出，`candidate` 仍停在已存在的 `_999` 上，并把一个存在的路径当作可用路径返回。概率极低，但方向上是"覆盖"而不是"拒绝"，与 M5-15 的性质一致，一并改掉：改成"找到第一个不存在的就 break，找不到就返回失败"。

**F5 · 缺任务卡与证据包（流程）**

`tasks/` 只有 G1/G2/G3，T-07/T-13/T-14 的证据只活在 `08` 的正文里。06 §4.1 规定"不接受对话中的口头指令"、§5.2 规定"一个需求一条证据、必须含可重跑命令"。当前是执行者自证 + 事后追记，这两条都没有守住。

### 2.4 实现设计（关键点，避免走弯路）

1. **媒体时钟与墙钟分离。** 帧 PTS 继续用"帧序号 × 帧时长"（确定性、总长精确，不动现有行为）；循环配速改用**只在 Recording 态前进**的媒体时钟。暂停期间媒体时钟冻结 → 恢复后不会突发补帧。
2. **暂停 = Stop 采集 + Stop 音频 + 冻结媒体时钟 + 不计入 `total_frames`。恢复 = Start 两者 + 重建 `AudioTimeline` + 等到第一帧（≤500ms，等不到就复制上一帧，最多 3 帧）。** DXGI/WGC `Stop→Start` 已有 `NeedsRebuild` 路径可复用。
3. **命令通道不引线程。** 在 `PipeConnection` 增加 `TryReceive(Message&)`：`PeekNamedPipe` 先看 12 字节头，`avail < 12 + payloadLen` 就返回 false（不消费），否则正常读。字节模式管道必须这样判，否则会把半帧读走。主循环每帧轮询一次，延迟 ≤ 1 帧（33ms），远低于 200ms 的门槛，也避免"关句柄打断阻塞读"这一类线程坑。
4. **注入不另造分支。** `--pause-at / --pause-for` 只做一个调度器，到点调用与管道命令**同一个** `ApplyControl(Pause/Resume)`。这与 T-13 用 `--disk-stop-mb` 把 stop 线卡到当前可用−2MB 是同一手法（`08 §12` 已论证过其正当性：触发的是完全相同的分支）。
5. **统计口径。** 新增 `media_seconds`（= 成片时长）、`paused_seconds`、`countdown_seconds`；`wall_seconds` 保留原义。验收断言一律用 `media_seconds`，不看墙钟。

### 2.6 轮 21 要点（倒计时 + 预设时长）

- 顺序必须是 **倒计时 → `PrepareOutputPath` → `muxer.Open`**。倒计时在路径准备之前，取消时连目录都不会被创建，天然满足"不产生任何文件"。
- 退出码 `14 = 用户取消`，输出 `cancelled=1`，不写 `output=`。这样脚本能区分"取消"和"失败"。
- `--seconds` 语义改为**媒体时长预算**（暂停不计入），`--countdown 0|3|5|10` 默认 0。
- 断言：倒计时 3s 时 stdout 出现 `countdown=3/2/1` 且间隔 1s±150ms；取消用例 `record_exit=14` 且目标目录不存在新建文件；`--seconds 6` → duration 6000±300ms、180 帧。

### 2.7 风险与回退

| 风险 | 信号 | 回退 |
| --- | --- | --- |
| 恢复时采集重建慢于 500ms | 恢复后前 3 帧为复制帧 | 允许复制补齐（不阻塞时间轴）；若 >1s 则改"保留采集、只停投递"（即 02 方案） |
