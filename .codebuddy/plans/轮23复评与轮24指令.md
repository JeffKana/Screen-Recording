## 3. 三个发现

**F1 · D-34：`.part.repaired` 仍会被覆盖（第 3 次同一个坑）**

`MkvRecovery.cpp:363`：

```cpp
std::filesystem::rename(source, source + ".repaired", rename_ec);
```

既没有避让，也没检查 `rename_ec`。Windows 的 rename 会覆盖已存在目标（D-24 的老问题）。实测：

```
before: 16 bytes   ← 预置的 .part.repaired 哨兵
repair=ok
after: 1343596 bytes  ← 被这次修复的源文件整体覆盖
```

影响有限（丢的是一份崩溃源副本，成品不受影响），但它是**静默覆盖**，且发生在你刚改过的那一行旁边。修法：避让 + 检查 `rename_ec`，失败则记 WARN 而不是当作已完成。

**F2 · 避让逻辑已经写了 3 份，其中 2 份还是旧语义**

| 位置 | 全占 999 时 |
| --- | --- |
| `OutputPath::FindFreePath`（轮 19 修） | 返回失败，拒绝覆盖 ✅ |
| `RepairIntoFallback`（轮 23） | 循环内 `if (!exists) break`，找不到就沿用已存在路径 ❌ |
| `MkvRecovery::Repair`（轮 23） | 同上 ❌ |

同一段 15 行逻辑写三遍，只有第一份是对的。建议抽一个公共函数（放 `platform` 或 `resilience` 头），三处共用——这是「修一次、错三处」的典型代价。

**F3 · 兜底只测了一种入口**

指令要求「录制中 / 收尾前 / 无 fallback 配置」三种情形。实际只有第一种有断言：

- **无 `--fallback-dir`** 时：代码有路径（保留 `.part`、`return fatal_code`），但无用例；
- **`.part` 不可修复**（如首簇就没写成）时：`RepairIntoFallback` 返回 false → 走 `return fatal_code`，同样无用例；
- **Close 阶段失败**（`close_failed` 分支）：未构造。

这三条都在你新写的 `if (fatal_code != 0 && integrity_lost)` 里，但没有一条被跑过。C 维度的 74.4 就是扣在这里。

**该记的正面**（这轮最值钱的两条）：

1. **D-33 的归因**：`remove` 失败是表象，根因是 `Close` 失败路径提前 return 没关句柄。「错误路径上的资源释放和成功路径一样需要显式处理」——这句话应该进交接模板。
2. **integrity_lost 的区分**：新增一条错误分支后立刻回跑既有错误路径用例，发现 `--fail-resume` 被误吞。这是 06 §10 反模式「修 bug 顺带改架构」的正确反面示范。

## 4. 你问的 TryReceive / 重叠 I/O / 多实例：我查了，结论是不需要重叠 I/O

事实（`PipeChannel.cpp`）：

| 项 | 现状 |
| --- | --- |
| `CreateNamedPipeW` 标志 | `PIPE_ACCESS_DUPLEX`、`PIPE_TYPE_BYTE`、`PIPE_READMODE_BYTE`、`PIPE_WAIT`、`PIPE_UNLIMITED_INSTANCES`、64KB 缓冲，**没有 `FILE_FLAG_OVERLAPPED`** |
| 读 | `ReadExact` → `ReadFile` **同步阻塞** |
| 接受连接 | `ConnectNamedPipe` **同步阻塞** |
| 多实例 | 名义 `UNLIMITED_INSTANCES`，但 `WaitForClient` 一次只持一个实例句柄；连上后立刻建下一个 → **串行重连可用，并发第二个客户端会 `ERROR_PIPE_BUSY`**（`PipeClient` 已有 `WaitNamedPipe` 3s 重试，对单 UI 够用） |

所以「UI 发暂停会阻塞在管道读上」这个担心是成立的——但**只有一种写法会真的阻塞**：在主循环里调 `Receive()`。
用 `PeekNamedPipe` 就不会：

1. `PeekNamedPipe(h, header, 12, &got, &avail, nullptr)` —— 只探不消费；
2. `avail < 12` → 返回 false；
3. 解析头得 `payloadLen`，`avail < 12 + payloadLen` → 返回 false（**半帧绝不消费**）；
4. 够一整帧才 `ReadFile`，此时数据已在缓冲区，不会长时间阻塞。

录屏主循环每帧调一次，延迟 ≤ 33ms，远低于 200ms 门槛，**不需要线程、不需要 `CancelIoEx`、不需要改 CONTRACT §7 的线格式**。

唯一需要阻塞的是「接受连接」。建议放在**录制开始之前**：`--control-pipe <name>` 时先 `WaitForClient`（超时 5s，超时则 `control=absent` 继续录，不失败），连上再进倒计时/开录。这样录制期间永不阻塞，也不用为 accept 造线程。重连不支持 → 记入已知限制。

## 5. 轮 24 指令（T-17a 控制通道 + 三个收尾项）

**计划轮次：2　截止判据：下述全绿**

### P0-1 `PipeConnection::TryReceive(Message&)`
按 §4 的 4 步实现（Peek 判整帧，不消费半帧）。
断言：连续发 8 条命令全部按序收到；人为把一条命令拆成两次写入时，前一次 `TryReceive` 必须返回 false 且**不丢字节**。

### P0-2 `--control-pipe <name>`
- 录制前 `WaitForClient(5000ms)`；超时 → `control=absent`，照常录制（不得失败）。
- 录制中每帧 `TryReceive`；命令映射：`Pause` / `Resume` / `Stop`（走与 `--pause-at` **同一处** `apply()` 与暂停流程）。
- 客户端断开 → `control_lost=1`，继续录制，不中断、不崩。
- 输出：`control=connected|absent|lost`、`commands_applied=`、`commands_rejected=`。

### P0-3 命令语义用例 `g4_channel.ps1`
| # | 场景 | 判据 |
| --- | --- | --- |
| 1 | `srctl pause` → 1s → `resume` | `paused_ms≥900`、成片时长不含暂停、`commands_applied=2` |
| 2 | `srctl stop` | 提前收尾、成品可播、`exit=0` |
| 3 | 重复 `pause` | 幂等，`paused_ms` 不翻倍、不崩 |
| 4 | `resume` 而当前非暂停 | `Rejected`，`commands_rejected=1` |
| 5 | 客户端中途退出 | `control_lost=1`，录制继续到点、成品可播 |
| 6 | 未连客户端（`--control-pipe` 超时） | `control=absent`，录制正常 |

### P1-1 D-34 + 避让去重
`.part.repaired` 加避让并检查 `rename_ec`；三处避让抽公共函数（全占 → 失败）。
断言：预置 16B `.part.repaired` 后修复，该文件**长度不变**。

### P1-2 兜底的两个缺口各补一条
- 无 `--fallback-dir` 时写失败：保留 `.part`、`exit=15`、不产生垃圾文件。
- `.part` 首簇未成形时写失败：`RepairIntoFallback` 失败 → `exit=15`、无 0 字节产物。

### P1-3 契约登记
`CaptureRequest::excluded_backend` 在 CONTRACT §4 补一行（运行期后端黑名单，供恢复期避让）；
main 的退出码表（0/6/10/11/12/13/14/15/16）写进 CONTRACT 或 README，验收脚本靠它判分支。

### 通过判据
`g4_channel` 全绿；`g4_control` 32/32、`g5_fallback` 21+、`g5_inject` 28/28、`g3_*` 15/11/9；契约 7/7；MSVC + MinGW 零告警。

### 硬边界
1. **不得为了非阻塞而引线程做阻塞读**，也不得用「关句柄打断阻塞读」（句柄复用会导致串话）。
2. 不得改 CONTRACT §7 的线格式；新用例必须复用 `srctl`，不得另造协议。
3. 若 `--control-pipe` 前置 accept 导致 `srctl` 连接时序不稳，加 `--control-wait <ms>` 调整，**不要**改成异步 accept。
