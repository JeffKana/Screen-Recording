## 现状（定性前的只读结论）

`src/encode/MfVideoEncoder.cpp:573-615` `PadToTargetBitrate()` 按**帧序号线性预算**：
`budget = target_per_sec*(idx_in_window+1)/fps`，`current = pad_bytes_in_window_ + 本包字节`；
只在 `budget > current` 时追加 filler NAL（type 12），超额时 `pad_bytes_in_window_ = current`
且不反向扣减；换秒时 `pad_bytes_in_window_ = 0`（超额债务清零，不结转）。
关键帧 + 运动画面的那几帧会把本秒撑到实测 9,539kbps（spread 58%）。

## 实测结论（2026-11-11，如实记录）

已按指令实现「按秒结算」（每帧按 `本秒剩余预算 / 本秒剩余帧数` 重算 filler 额度 +
换秒时显式记账），三构建零告警，并在**同一组 5+5 次 CBR 40s** 上验证：

| 模式 | 定性前（旧口径） | 按秒结算后 |
| --- | --- | --- |
| 静态 5 次超 10% | 4/5 | **3/5**（84.4% / 295.2% / 108.4% / 1.5% / 3.3%） |
| 运动 5 次超 10% | 5/5 | **5/5**（19.3% ~ 24.9%） |
| 运动 avg | 6,276 kbps（偏差 4.6%） | **8,039 kbps（偏差 34%）** ← 新回归 |

**未达成判据，且引入新回归**：运动源 avg 超标称 34%，会额外触发
`m3-04-cbr-nominal`（≤20%）FAIL。根因是 filler 是只增不减的 H.264 NAL：
当某秒的真实编码输出（IDR + 运动画面 P 帧）本身已超 750,000 B，
任何 filler 口径都无法把已写入容器的字节削回来。

因此**回滚本次产品改动**（`PadToTargetBitrate()` 与相关字段恢复轮 42 原状），
保留 10 次实测作为「指令指定的修法已尝试、经实测不适用」的红绿证据；
`M3-04#1` 保持「有卡未实现」，缺陷单与裁定选项见 `docs/17`。
回滚后三构建再次零告警（`tasks/G6/V1-007/artifacts/build-summary.txt`）。
**执行方不假绿、不为保住覆盖数字留一个让产品变差的改动。**
