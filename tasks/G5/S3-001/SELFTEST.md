# SELFTEST: S3-001 故障注入

## 1. 注入时刻必须晚于两个 Cluster（本轮第一坑）

首版强杀在 3s，恢复结果为 0 字节可修复文件。原因不是产品缺陷：
1.5s/簇时，3s 只有首簇在写、被杀即整簇作废，磁盘上没有任何**完整**簇。

判据：`MkvRecovery` 要求「至少一个完整 Cluster」，因此注入时刻必须 ≥ 3s + 余量。
最终改为 8s / 9s / 4.7s 三个场景。

## 2. 磁盘注入的阈值不能循环外算一次

第 1 轮写出 2.7MB 后，第 2、3 轮用同一个 stop 线会直接命中「开录前拒绝（exit 12）」，
测到的是另一条分支，看起来像「行为不一致」。改为每轮重算。

## 3. 一致性断言不能包含抖动量

`Test-Consistent` 最初把文件大小拼进判定串，三轮大小不同 → 误报「不稳定」。
一致性只应比对**判定元组**（stop/code/part/playable）。

## 4. 「暂停中强杀」暴露的真实缺陷（D-30）

进入暂停时不落盘，暂停期被杀丢失整个未落盘簇（3.44s）。
加 `FlushPending()` 后 4.97s。剩余 ~1s 是编码器内部缓冲，未强行 DRAIN。

## 5. 判定阈值要来自需求，不来自我的推演

一度把判据收紧成「丢失 ≤3.5s」，导致正常行为被判失败。
回到 01/05 的原文「恢复到崩溃前 ≤10s」，并把实测损失作为 INFO 输出。
