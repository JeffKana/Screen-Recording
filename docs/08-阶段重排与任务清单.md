## 5. 关键技术约束（本次 WGC 的核心风险）

WGC 是 WinRT API，**必须通过 C++/WinRT 头使用，只有 MSVC 能编译**。

- 因此 T-03 不是可选项：`src/capture/` 内 WGC 实现必须用 `#ifdef SR_HAS_WGC` 隔离，
  MinGW 构建时该文件为空实现，工厂自动选择 DXGI。
- 链接需 `windowsapp.lib`。
- WGC 的窗口采集需要 `GraphicsCaptureSession::IsSupported()` 运行时探测，不支持时返回
  `UnsupportedSource` 错误码，由工厂降级，不得崩溃。
- 光标：WGC 原生可绘制光标（`IsCursorCaptureEnabled`，Win10 2004+），与 02 §4.2 的
  「自绘光标」路径互斥，开关逻辑要显式处理。
- 边框：`IsBorderRequired`（Win11）关闭黄色采集边框，老系统该 API 不存在，需版本判断。

## 6. 风险与回退点

| 风险 | 触发信号 | 回退动作 |
| --- | --- | --- |
| WGC 对某些窗口返回黑帧 | T-04 用例中黑帧比例 > 50% | 保留 PrintWindow 作为该窗口的兜底，WGC 仅用于显示器与已知窗口 |
| C++/WinRT 与现有 D3D11 代码互操作困难 | 编译或纹理共享失败 | WGC 仅用于窗口源，显示器继续 DXGI DD（两者本就职责重叠） |

实现要点：

1. **恢复不重编码**：利用 ADR-02 的「Segment 未知长度 + Cluster 已知长度」，
   截断到最后一个完整 Cluster 即得到合法文件，再按大端回填 Duration。
2. **可恢复性判定**：需同时满足「Tracks 里有 V_MPEG4/ISO/AVC」且「至少 1 个完整 Cluster」，
   否则标记为不可修复，绝不覆盖原文件。
3. **时间基一致**：`last_pts` 来自 Cluster Timecode + SimpleBlock 相对时间，
   与写入端同源，避免修复后时长与画面错位。

已知限制：丢失窗口 = 未落盘 Cluster（≤1.5s）+ 正在写的半个 Cluster，
实测 2.56s。若要压到 1s 内，应缩短 Cluster 间隔（代价是容器开销上升）。

## 12. T-13 存储守护执行结果（2026-10-21）

用例 `verify/cases/g3_storage.ps1`：**11 PASS / 0 FAIL**。

| 判据 | 结果 |
| --- | --- |
| M8-05 可用空间可读、可录时长可算 | 202 GB → 260898 秒（6192 kbps），公式 `(free − stop) / (bitrate/8)` |
| M8-03 低水位提示 | `disk_warn=1`，提示「剩余 X MB，约 Y 秒」 |
| M8-04 耗尽前安全停止 | 请求 30s，实到 9.07s 触发提前收尾；`disk_stop=1`；产物 2.7 MB 可播 |
| M8-04 不产生 0 字节文件 | 结构核验 0 failure，ffmpeg 解码零错误，无 `.part` 残留 |
| 开录前拒绝 | `record_exit=12`，且不留下碎片文件 |

关键实现决策：

1. **独立 stop 线而非「写失败再处理」**：写满时最后一次写入可能只落一半，封装层来不及
   写 Duration/Cluster，产物直接不可播。提前停才有机会正常收尾。
2. **注入方式**：把 stop 线卡到「当前可用 − 2 MB」，触发的是与真实耗尽**完全相同的分支**
   （`must_stop → break → 正常收尾`）。不采用真写满磁盘，因为不可重复且会破坏机器。
3. **用 `available` 而非 `total_free`**：磁盘配额与受控文件夹访问下两者不同，前者才是能写进去的量。

已知限制：`estimated_seconds` 按**配置码率**估算，屏幕内容实际码率远低于上限，
因此该值是保守下界（本机实测：估算 260898s，而实际 30s 录制仅写入 9 MB）。
这是刻意的——估高会误导用户，估低只是提前提醒。

## 19. 轮 25：§7 握手补正（T-17a 返工）

评审指出的核心缺口成立：控制通道**没有实现 §7 的 Hello/HelloAck 握手**，导致

1. 唯一现成客户端 `srctl` 连上即阻塞（它发 Hello 后等 Ack），不可用；
2. 验收只能用自造客户端，证明的是「自定义客户端可用」；
3. 无令牌校验，本地任意进程可停别人的录制。

而 CONTRACT §18.3 当时把七条判据全标 PASS —— 契约自相矛盾。

### 修复

| 项 | 实现 |
| --- | --- |
| 握手 | Hello{token} → 校验 → HelloAck{version,pid,state} → **紧跟一条初始 StateSnapshot** |
| 令牌 | `--control-token`，默认 `dev`；不匹配直接断开，`control=rejected` |
| 未握手 | 1s 内未收到合法 Hello 一律断开，不宽容处理 |
| 重连 | 每秒 `TryAcceptClient` + 重新握手（支持多次 srctl 调用 / UI 重启） |
| 命令回执 | 每条命令后回 StateSnapshot，且回报「命令生效后的目标状态」 |

`srctl` 在 Ack 之后会阻塞等初始快照——只回 Ack 会让客户端挂在 `Receive` 上，
这是首轮返工的直接原因。

### 用例重写

`g4_channel.ps1` 全部改用 `srctl`（硬边界）。唯一例外是帧切分场景：`srctl` 无法发送半帧，
该场景只做字节级写入、不实现协议解析，且已在脚本头注明。

新增场景：Stop（提前收尾、`Stopping,Idle`）、暂停中 Stop（不得多一次 Recording）、错误 token。
