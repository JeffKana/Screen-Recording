# 03 · 技术选型

> 每个维度给出候选对比与**唯一结论**。结论附带代价说明 —— 没有免费的选型，只有被显式接受的代价。

## 1. 选型前提约束

在开始比较之前，先把不可谈判的约束定下来，否则比较会失焦：

| 约束 | 来源 | 对选型的影响 |
| --- | --- | --- |
| 只做 Windows，且 Win10 1903+ 为下限 | M6-05 | 采集可放心用 WGC（1803+ 可用），但必须为 1903 的 API 子集留兜底 |
| 只用用户态，不装驱动 | M6-10、README 定位 | 排除所有依赖内核过滤驱动（如虚拟摄像头、内核级 hook）的方案 |
| 采集必须出 GPU 纹理 | M6-01、M6-02 | 排除「截一张 BGRA 图再 CPU 转码」的简单方案 |
| 硬编优先 + 确定性软编回退 | M3-06、M8-08 | 必须同时具备至少一条硬编链路和一条永远可用的软编链路 |
| 录制中可崩溃恢复 | M8-01 | 封装层必须支持分片与容器容错 |
| 分发为闭源商业软件 | 产品形态 | 许可必须允许闭源动态链接；GPL 组件需隔离或替换 |

## 2. 语言与运行时

| 候选 | 优势 | 劣势 | 结论 |
| --- | --- | --- | --- |
| **C++20 + MSVC 2022** | 与 COM / D3D11 / Media Foundation 零摩擦；硬编 SDK 全部是 C 接口；内存与线程可控，适合实时路径 | 内存安全靠纪律，开发效率低 | **采用**（引擎 + UI 全用 C++） |
| Rust | 内存安全、并发模型好 | Windows 采集与硬编 SDK 的绑定不成熟，D3D11 与 MFT 需大量 unsafe 封装；生态里缺少成熟的 WGC 高封装 | 放弃：实时音视频路径的 unsafe 面积并不比 C++ 小，收益不成立 |
| C# / .NET | 开发效率高，WinRT 互操作有官方支持 | GC 抖动直接影响采集回调；硬编需 P/Invoke；进程常驻内存偏高 | 放弃：M6-01 的占用目标与 GC 天然冲突 |
| C++ 引擎 + C# UI | 界面开发快 | 双运行时、双构建链、跨进程调试成本 | 放弃：收益不足以抵消复杂度（双进程已经把隔离做到了） |

**构建工具**：CMake + vcpkg（manifest 模式锁版本）。理由：硬编 SDK 均为二进制包，vcpkg 的 port 机制能统一版本与编译选项；MSBuild 单独管理三方依赖易漂移。

## 3. UI 框架

| 候选 | 与引擎互操作 | 开发效率 | 许可 | 风险 |
| --- | --- | --- | --- | --- |
| **Qt 6（QML + C++）** | 同进程原生 C++，共享纹理可直接交给 `QRhi`/自定义渲染 | 高（QML 声明式） | LGPLv3（动态链接可闭源） | 需遵守 LGPL：动态链接、允许替换、附许可声明 |
| WinUI 3 | 需 WinRT 互操作，跨进程传纹理要绕路 | 中 | MIT | 与 C++ 引擎同进程时 COM 生命周期管理复杂；高 DPI 与多屏切换历史 bug 较多 |
| WPF | 需 C++/CLI 或 P/Invoke 桥 | 中高 | MIT | 引入 .NET 运行时与 GC，违背上一条结论 |
| Electron / Tauri | 前端生态好 | 高 | MIT | 内存占用与启动时间与「低占用」目标冲突 |

**结论（2026-10-22 轮 27 确认）：V1.0 走 Win32 原生回退，Qt 6 留给 V1.5。**

- **V1.0**：`src/app/` 用 Win32 原生实现（`Shell_NotifyIcon` + `RegisterHotKey` + 普通窗口/控件）。
  V1.0 的 UI 面只有 12 条系统级控件（托盘、热键、倒计时、暂停、保存路径、自检提示），
  Qt 6 的收益主要来自 V1.5 的编辑时间轴，而不是 MVP。原生实现没有 Qt 运行时与
  动态链接/LGPL 声明成本，启动与常驻内存也更贴近「托盘空闲 ≤1% CPU」的目标。
- **V1.5**：编辑时间轴改用 Qt 6（QML + C++，LGPLv3 动态链接）。UI 与 Recorder 只通过
  命名管道通信，`src/app/` 的替换不触及采集/编码/封装，迁移成本被限制在 UI 进程内。
- **隔离**：Recorder 进程不链接任何 UI 框架；`src/app/` 也不链接 capture/encode/mux，
  只依赖 `sr_ipc` / `sr_core`（见 `src/app/CMakeLists.txt`）。

Qt 6 的代价与规避（V1.5 生效）：

- 必须**动态链接** Qt 库并在关于页附 LGPL 声明与源码获取方式，不静态链接。
- 不用 Qt 的 GPL-only 模块（如 Qt Charts 的旧版、Qt Virtual Keyboard 部分模块），选型时逐一核对模块许可。

## 4. 屏幕与窗口采集

| 候选 | 采集对象 | 遮挡后能否采集 | 输出形态 | 性能 | 关键限制 |
| --- | --- | --- | --- | --- | --- |
| **WGC（Windows.Graphics.Capture）** | 显示器 + 单窗口 | **能** | D3D11 纹理 | 好（GPU 内） | Win10 1803+；光标/边框开关为 2004+ 的 API，需做版本探测；UAC 提权窗口与非同进程权限下采集为黑屏 |
| DXGI Desktop Duplication | 仅整屏 | 能 | D3D11 纹理 | 最好（延迟最低） | 只支持整屏，无法按窗口；独占全屏切换时需重建；多显卡跨适配器受限 |
| GDI BitBlt | 整屏 / 区域 | **不能**（取到的是屏幕像素） | CPU 位图 | 差（CPU 拷贝 + 无硬件缩放） | 高分辨率高帧率下 CPU 占用极高；仅作兜底 |
| PrintWindow(PW_RENDERFULLCONTENT) | 单窗口 | 能 | CPU 位图 | 差 | 部分 UWP 与 GPU 渲染窗口返回黑图；不能在采集回调里高频调用 |
| 桌面窗口管理器（DWM）截屏重定向 | — | — | — | — | 无公开稳定 API，放弃 |

**结论：三级路径 + 按需组合**

1. **主路径 WGC**：覆盖显示器与窗口两类源，满足 M1-01/02/04/07/09。
2. **补充路径 DXGI Desktop Duplication**：仅在全屏/独占全屏游戏场景启用（M6-07 相关），由用户设置「游戏模式」触发，或由 WGC 连续丢帧自动切换。
3. **兜底路径 GDI BitBlt**：WGC 与 DXGI 均不可用时启用，界面明确提示「当前为兼容模式，帧率受限」。
4. 窗口采集失败帧（连续黑帧）→ 单次尝试 `PrintWindow(PW_RENDERFULLCONTENT)` 取证，仍失败则提示该窗口不支持（对应 M1-09 的边界）。

代价：三条路径意味着**三套测试矩阵**，这是本方案最大的兼容性成本来源；因此 GDI 兜底在 V1.0 只保证「能录出画面」，不承诺帧率。

## 5. 音频采集与混音

| 候选 | 用途 | 延迟 | 结论 |
| --- | --- | --- | --- |
| **WASAPI Loopback（共享模式 + 事件驱动）** | 系统声音 | 低 | **采用**。`IAudioClient3` 可进一步降低缓冲，但 Win10 1803+ 才有，需版本判断后用 `IAudioClient` 兜底 |
| WASAPI Loopback（独占模式） | 系统声音 | 最低 | 放弃：独占模式会**抢走**音频设备的独占权，导致用户其他程序无声，不可接受 |
| WASAPI Capture | 麦克风 | 低 | **采用** |
| DirectShow / Media Foundation 音频源 | 麦克风 | 中 | 放弃：多一层封装，热插拔与设备切换处理不如直接 WASAPI |
| 第三方虚拟声卡驱动 | 系统声音 | — | 放弃：违反「不装驱动」约束 |

### 5.1 Loopback 的三个坑（必须在设计阶段解决）

1. **静音期无数据包**：共享模式 Loopback 在系统无音频输出时**不产生数据包**（不是产生静音包）。若直接按包计数推进时间轴，音频时长会短于视频，导致音画不同步。→ 对策：以「已流逝的 QPC 时间」为准计算应得样本数，缺多少补多少静音（M1-21）。
2. **设备默认切换**：用户插拔耳机导致默认设备变更时，原 `IAudioClient` 会静默停止。→ 对策：注册 `IMMNotificationClient`，在 `OnDefaultDeviceChanged` 时重建流并补齐时间戳（M8-11）。
3. **格式不统一**：不同设备的混音格式可能是 16bit/24bit/32bit float、不同声道数。→ 对策：统一转换为 **float32 交错** 后再混音，混音器内部只处理一种格式。

### 5.2 混音与降噪

- **混音器**：自研 float32 混音器，支持单轨混合与双轨独立（M1-18/M1-19），带峰值限幅（防削波）。约 300 行代码，引入第三方库不划算。
- **降噪（V2.0）**：候选 WebRTC Audio Processing（BSD，含 AEC/NS/AGC）与 RNNoise（BSD）。**结论：WebRTC APM** —— 一套库同时提供噪声抑制与自动增益，正好覆盖 M1-22 两项诉求。

## 6. 视频编码

| 候选 | 类型 | 输入形态 | 许可 | 风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| **NVENC（NVIDIA）** | 硬编 | D3D11 纹理直入 | SDK 免费，需遵守 SDK 许可 | 驱动版本与 GPU 代际决定能力（如 H.264 并发会话数限制） | **采用**（N 卡主路径） |
| **oneVPL / QSV（Intel）** | 硬编 | D3D11 纹理直入 | oneVPL 开源（MIT），硬件需 Intel 核显/Arc | 老平台仅支持 H.264；驱动兼容性一般 | **采用**（I 卡 / 核显路径） |
| **AMF（AMD）** | 硬编 | D3D11 纹理直入 | SDK 开源 | 编码质量历史口碑弱于 NVENC/QSV，需按型号调参 | **采用**（A 卡路径） |
| Media Foundation H.264 MFT（硬件） | 硬编（系统封装） | D3D11 纹理 | 系统自带 | 对上层暴露的参数少，能力探测粒度粗 | 作为**统一抽象层的参考实现**，不作为主路径 |
| **Media Foundation H.264 软件 MFT** | 软编 | CPU 内存 | 系统自带，无额外许可 | 画质与速度不如 x264，参数少 | **采用为软编回退首选**（M3-06/A8-08 的兜底） |
| libx264 | 软编 | CPU 内存 | **GPLv2** | 闭源分发需遵守 GPL；商用需另购许可 | 仅作为可选构建项，默认不打包 |
| libopenh264 | 软编 | CPU 内存 | BSD（Cisco 承担专利费，限其二进制） | 需使用 Cisco 官方二进制下载机制 | 备选回退，若 MF 软编在某些机器上不可用则启用 |
| **SVT-AV1 / libaom** | 软编 AV1 | CPU 内存 | 开源（BSD/AOMedia） | 编码速度对实时录制不友好 | V2.0 仅作转码用途，不用于实时录制 |

**结论：硬编三厂商 + MF 软编 MFT 回退。**

这带来一个必须正视的结论：**为了规避 GPL，主动放弃了画质最优的 x264**。这在 1080p 场景影响可接受（MF 软编足够），在 4K 软编场景会成为短板 —— 记为已知限制，V1.5 评估是否引入商业授权的 x264 或改用 openh264。

### 6.1 色彩转换与缩放

必须由 **D3D11 VideoProcessor** 在 GPU 完成 `BGRA → NV12 + 缩放`。三条理由：

1. CPU 回读 4K 帧（约 33MB/帧）在 60fps 下需 2GB/s 的内存带宽，直接压垮内存子系统。
2. libswscale 在多线程下的性能与 GPU VideoProcessor 差距是数量级的。
3. 硬编要求 NV12 输入且必须来自 D3D11 纹理才能零拷贝。

**代价**：部分老 GPU 不支持 VideoProcessor 对特定分辨率/格式的组合，需在探测阶段枚举能力并回退到 CPU 路径（此时明确降级帧率）。

### 6.2 硬件能力探测与降级矩阵

| 探测项 | 探测方式 | 不满足时的降级 |
| --- | --- | --- |
| 硬编是否可用 | 各 SDK 的 `GetEncoderCaps` / `MFEnumEx` | 下一个厂商 → MF 软编 |
| 最大分辨率/帧率 | SDK 能力查询（按 codec 分别查） | 参数面板置灰 + 自动降到能力上限 |
| 10bit 支持（M3-16） | 能力查询中的 profile 列表 | 回退 8bit 并提示 |
| D3D11 纹理输入支持 | SDK 文档能力位 | CPU 中转（降帧率） |
| VideoProcessor 能力 | `CheckVideoProcessorFormatConversion` | CPU 色彩转换 |
| WGC 光标/边框开关 API | 系统 build 号判断 | 老系统用原生默认行为 |
| 显示器 HDR | `IDXGIOutput6::GetDesc1` 的 `ColorSpace` | 走 SDR 路径（M1-26 前提） |

## 7. 音频编码

| 候选 | 许可 | 结论 |
| --- | --- | --- |
| **Media Foundation AAC MFT** | 系统自带 | **采用**：零额外依赖，满足 192kbps 立体声需求 |
| libavcodec 原生 AAC 编码器 | LGPL（随 FFmpeg 构建） | 备选：MF 在某些精简版系统上 AAC MFT 缺失时启用 |
| libfdk_aac | 非自由许可，不可再分发 | 放弃 |
| Opus | BSD | V2.0 可选（MKV 容器下体积更优），MP4 兼容性差，不作为默认 |

> MP4 + AAC 是兼容性最好的组合；若 AAC MFT 缺失概率高于预期，则默认容器切 MKV + Opus，但这会牺牲「双击即播」体验，因此优先保证 AAC 可用性。

## 8. 封装与媒体库

| 候选 | 能力 | 许可 | 结论 |
| --- | --- | --- | --- |
| **FFmpeg（libavformat + libavcodec，LGPL 构建）** | 封装、remux、解封装、转码、字幕 | LGPL 2.1+（需 `--disable-gpl`，避免链入 x264 等 GPL 组件） | **采用**：remux（M5-04/M8-02）、编辑导出（M4）、格式转换（M5-11）都依赖它 |
| 自研 MP4 muxer | 只写 MP4 | 自有 | 放弃：分片/多音轨/时间戳重排/MKV 都要重写一遍 |
| Media Foundation SinkWriter | 系统封装 | 系统自带 | 放弃：分片与自定义 AVIO 能力弱，无法满足「崩溃可恢复」 |
| libmp4v2 / Bento4 | 仅 MP4 | 各异 | 放弃：功能面窄于 FFmpeg |

**构建约束（关键）**：FFmpeg 必须用 `--disable-gpl --disable-nonfree` 构建，且**不得**链接 libx264/libx265/libfdk-aac。否则整个应用被传染为 GPL。这一条要写进 CI 的依赖白名单检查。

## 9. 摄像头采集

| 候选 | 结论 |
| --- | --- |
| **Media Foundation SourceReader** | **采用**：可协商 MJPG/YUY2/NV12，能直接输出到 D3D11 纹理（`MF_SOURCE_READER_D3D_MANAGER`），与合成层零拷贝 |
| DirectShow | 放弃：老 API，设备枚举与格式协商更繁琐 |
| Windows.Media.Capture（WinRT） | 放弃：需 WinRT 互操作，且对格式控制粒度不如 SourceReader |

## 10. 许可与分发约束汇总

| 组件 | 许可 | 闭源分发是否可行 | 必须做的事 |
| --- | --- | --- | --- |
| Qt 6 | LGPLv3 | 可行（动态链接） | 动态链接、附许可文本、提供替换库的方法说明 |
| FFmpeg（LGPL 构建） | LGPL 2.1+ | 可行 | 同 LGPL 义务；确保未链入 GPL 组件 |
| libx264 | GPLv2 | **不可**（除非开源或购买商业许可） | 默认不打包 |
| NVENC SDK | NVIDIA SDK 许可 | 可行 | 遵守 SDK 条款，不反向工程 |
| oneVPL | MIT（SDK） | 可行 | 保留版权声明 |
| AMF | MIT | 可行 | 保留版权声明 |
| WebRTC APM | BSD | 可行 | 保留版权声明 |
| H.264 / HEVC 专利池 | MPEG LA / Via LA / Access Advance | 需评估 | 商业分发前评估专利许可义务（**非代码问题，需法务确认**） |
| AV1 | 免专利（AOMedia） | 可行 | 无 |

> **必须提前暴露的风险**：H.264 专利许可与 HEVC 专利池是商业分发绕不开的成本项。技术上「能编码」不等于「可合法分发」。这条在立项评审时就应交由法务确认，不能等到发版前。

## 11. 风险与验证清单（Spike 任务）

每个 Spike 都是「如果不成立，方案要改」的假设，必须在 V1.0 开发前用 1~3 天验证完毕。

| 编号 | 待验证假设 | 验证方式 | 若不成立的应对 |
| --- | --- | --- | --- |
| S-01 | WGC 在目标机群上对主流窗口（Chrome/Office/UWP）稳定采集 | 在 3 台机器 × 10 个常见应用上各录 5 分钟 | 加大 PrintWindow 兜底权重，窗口采集标注为「部分应用不支持」 |
| S-02 | 混合 DPI 下 WGC 返回的纹理与选区坐标可精确对应 | 150% + 100% 双屏下录制区域并比对像素 | 采集层引入坐标归一化中间层 |
| S-03 | 三家硬编均可接受 D3D11 纹理输入且无明显额外延迟 | 各厂商各测一次 1080p60 / 4K30 | 该厂商降级为 CPU 中转路径 |
| S-04 | WASAPI Loopback 静音填充方案在 8 小时下不产生累积漂移 | 8 小时录制 + 首尾拍手基准 | 引入周期性重采样校正 |
| S-05 | 分片 MKV 在强制断电后可被 libavformat 修复 | 断电测试 10 次，统计修复成功率 | 提高分片频率（缩短单分片时长） |
| S-06 | D3D11 共享纹理跨进程预览延迟可接受 | 测量预览端到端延迟 | 预览降帧率或改为缩略图 |
| S-07 | MF H.264 软编在 1080p30 下能实时 | 单机压测 | 引入 openh264 作为第二软编 |
| S-08 | Qt 6 与 D3D11 纹理互操作可行（V1.5 编辑时间轴前置） | 最小 Demo 渲染共享纹理 | 预览改为 CPU 回读（仅预览，不影响录制） |

## 12. 推荐技术栈总表

| 层 | 选择 |
| --- | --- |
| 语言 / 编译器 | C++20 / MSVC 2022 |
| 构建 | CMake + vcpkg（manifest 锁版本） |
| UI | V1.0：Win32 原生（托盘/热键，无第三方 UI 运行时）；V1.5：Qt 6 QML（LGPL 动态链接），仅 UI 进程使用 |
| 图形 | D3D11（采集纹理、合成、色彩转换、共享纹理） |
| 屏幕采集 | WGC（主）→ DXGI Desktop Duplication（游戏/全屏）→ GDI BitBlt（兜底） |
