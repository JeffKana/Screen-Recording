## 7. 本轮新发现 `F1-51`：`moov` 随时长线性增长，「前 64KB」不是通用门槛

### 7.1 事实（可重跑）

```powershell
# 240s / 40Mbps / mp4，1.15GB
.\build-msvc\bin\Release\sr-recorder.exe --record --seconds 240 --fps 30 --bitrate 40000 --format mp4 --out base.mp4
python verify/tools/mp4_box_check.py base.mp4
```

| 素材 | 文件大小 | `moov` 起点 | `moov` 结束（= moov 体积） | 顶层布局 |
| --- | ---: | ---: | ---: | --- |
| 5s（`g5_mp4` 样本） | 1.4MB | 32 | **5,232 B** | `ftyp@0 moov@32 mdat@5232` ✔ 前 64KB |
| 240s（本轮） | 1,150MB | 32 | **198,052 B** | `ftyp@0 moov@32 mdat@198052` ✔ 前置、✘ 前 64KB |

机制：`Mp4Writer` 目前**每个样本一个 chunk**（`stsc` entries = 样本数），于是
`stsc/stsz/stco`（必要时 `co64`）与 `ctts` 的表项数 = 帧数/样本数，`moov` 体积随时长**线性增长**：

- 视频：7200 帧 → `stsz` 28.8KB + `stco` 28.8KB；8h（864,000 帧）→ 各 ≈3.4MB；
- 音频：≈1.24M 个 AAC 帧 → `stsz`+`stco`+`ctts` 各 ≈5MB；
- **8h 外推 `moov` ≈ 20MB 量级**，仍在文件头部（faststart 成立），但"前 64KB 内可解析"必然为假。

### 7.2 两种裁定方向（本卡不自行选择）

| 方向 | 做法 | 代价 / 风险 |
| --- | --- | --- |
| **A. 拆判据（推荐）** | 把「faststart 成立」与「前 64KB 可完整解析 moov」拆成两条：前者是**通用门槛**（`moov` 偏移 < `mdat` 偏移，任何时长都成立，现已满足）；后者降级为**短素材启发式**（如 ≤60s 样本上验证，仅证明"容器头足够小、首帧起播快"），不作为通用门槛 | 需改轮 49 卡判据 #4 的措辞与 `mp4_box_check.py` 的 `moov-in-first-64k` 断言口径（**改判据**，须验收方/O0 书面同意） |
| **B. 改实现** | `stsc` 改为多样本/chunk（约每 1s 一个 chunk），`stco` 表项数降到原来的 1/30 → 8h `moov` ≈ 0.7MB | 属**加功能/改实现**，与轮 51「不加功能」冲突；且 `co64` 与偏移计算、`g5_mp4` 的 `stsc-one-sample-per-chunk` 断言（现断言"每样本一个 chunk"）都要一起改 |

**本人建议 A**：本产品的 faststart 目标是"起播快、可边下边播"，`moov` 在头部即已达成；
"前 64KB" 是 5s 样本上观察到的巧合数值，把它当通用门槛会让判据在长录制上必然失败。
若验收方要保留"前 64KB"，则必须走 B 并把 `g5_mp4` 的 `stsc-one-sample-per-chunk` 断言一起改。

### 7.3 这一条对 rc / GA 的影响

- **不影响 rc.1 已发布产物的可用性**：默认 MKV，MP4 是 opt-in，且 `moov` 前置成立、`ffmpeg` 全解码零错；
- **影响的是判据表述**：`docs/22` 判据 ① 里 M3-09#1 的"前 64KB"若被当成硬门槛，长录制一律不合格；
- 本轮按"不改判据"处理：只记录、不定级过高（一般级），交验收方裁定。
