# 23 · V1.0-rc 发布定位与口径

> 2026-11-18 · O0 裁定（用户拍板）· 生效：0.1.0-rc.1
> 一句话：**V1.0 定位为「内部可用版本」，先发 rc；真机验证补齐后再谈对外 GA。**

---

## 1. 为什么这么定

`docs/05 §7.2` 的六条发布判据里，① 的真机部分、⑤ 矩阵、⑥ 性能基线、③ 长稳 3 次，都依赖**当前不具备的硬件与环境**。代码侧已无未实现功能（111/116 子句，其余 4 条 BLOCKED 在真机）。

继续等机器 = 无限期延期；直接对外 GA = 结论宽于证据。**rc 是第三条路：让产品先可用，同时把「未证明的部分」写在明面上。**

---

## 2. rc 的定义

| 项 | 定义 |
| --- | --- |
| 是什么 | 功能完整、可日常录制，但**验证覆盖不完备**的候选版本 |
| 给谁用 | 项目内部、可接受风险的自用与他用；**不作为对外售卖/宣传版本** |
| 不允许说 | 「V1.0 完成」「生产可用」「全平台通过」「8 小时稳定」（LT 仅 1 次） |
| 允许说 | 「V1.0-rc，功能完整，真机兼容性与长稳验证进行中」 |

---

## 3. rc 门禁（与 GA 的差异，逐条对齐 §7.2）

| # | GA 判据 | rc 门槛 | 差异理由 |
| --- | --- | --- | --- |
| ① | 66 条全过 | **111/116 子句已实现**；4 条真机 BLOCKED + `M1-27#1` 例外**须在发布说明中逐条列明** | 真机不可得，但缺口必须公开 |
| ② | 阻塞级 0、严重 ≤3 有计划 | 同 GA：**阻塞级必须 0** | 这条不能松 |
| ③ | LT 各 3 次 | **LT-01 ≥1 次 8h、LT-02 ≥1 轮** | 3 次是统计意义，rc 接受单次实测 |
| ④ | ER 各 3 次 | 历史证据即可，但**代理性质必须标注** | 不再重跑以省窗口 |
| ⑤ | 矩阵必测 100%/抽测 80% | **已测格如实标注，未测格写明"未测"** | 不允许把未测写成通过 |
| ⑥ | B 机性能基线 | **缺基线，发布说明标注"未测"** | 缺机器 |

> 关键：rc **松的是"样本量与机型覆盖"，不松"结论真实性"**。任何一项没做的事，必须在发布说明里出现，且不得使用肯定性措辞。

1. `M6-01#1` / `M6-04#1` / `M6-05#1` / `M6-08#1` 四条真机子句有实测证据（或 O0 书面例外）；

## 6. rc 期间的工作方式

- 每轮仍走 `round/NN` 分支 + PR + CI + 验收（SOP 不变）；
- 缺陷分级照 GA 标准，**阻塞级一律不发 rc 补丁**；
- rc 补丁版本 `0.1.0-rc.2`、`rc.3`…，每次附「修了什么 + 新增什么证据」；
- 对外 GA 前，`docs/22` 的六条判据必须全绿，不允许"以 rc 名义长期对外"。

---

## 7. 发布说明必须包含的四段

1. **能做什么**（功能清单，别夸大）；
2. **已知限制**（至少：MP4 崩溃不可恢复、UAC 提权窗口黑屏、硬编在本机不可用、150% DPI 未实测、真机矩阵未覆盖、长稳仅 1 次）；
3. **不要用它做什么**（别用于合规留证、别用于无人值守长跑）；
4. **怎么反馈**（issue 模板：构建 SHA + 诊断包）。

---

## 8. rc 期缺陷如何分级、什么时候发 rc.2

> 轮 51 补。**rc 不是「免除分级」的许可证**：分级标准与 GA 完全相同（`docs/05 §7.1`），
> 变的只是「发不发新版本的节奏」。

### 8.1 分级（照 `docs/05 §7.1`，不新增级别）

| 级别 | 本产品的具体口径 | rc 期处理 |
| --- | --- | --- |
| 阻塞 Blocker | 录制无法完成、产物打不开、进程崩溃、丢音轨 | **立即停发**，修完发 rc.2；修不完不发 rc.2，宁可停在 rc.1 |
| 严重 Major | 音画同步 >500ms、选区错位、内存持续上涨、文件被静默覆盖 | 累计 **>3 条**或出现「无处置计划」的一条 → 发 rc.2；≤3 条且有计划 → 可随 rc.2 一并修 |
| 一般 Normal | 提示文案错误、极端场景回退、少量丢帧 | 攒批，随下一次 rc.2 / GA 修，不单独发版 |
| 轻微 Minor | 对齐、字体、翻译 | 同上 |

### 8.2 rc.2 的触发条件（满足任一即发）

1. **出现 1 条阻塞级缺陷**（含回归：rc.1 能用、rc.2 候选构建不能用 → 同样算阻塞）；
2. **严重级累计 >3 条**，或某条严重级被验收方判为「无处置计划」；
3. 修复了 `docs/24` 已登记「已知限制」中的一项（例如 MP4 崩溃恢复、UAC 黑屏终审），需要让用户拿到新证据；
4. O0 明确要求出包（例如某真机提供方需要带修复的构建做兼容性实测）。

**不触发 rc.2 的情况**：只改了文档/台账/用例、只补了验证证据（不改二进制）、
只有一般/轻微级缺陷。这些走分支 + PR，但不发版。

### 8.3 rc.2 必须附什么

- 「修了什么」：逐条对应缺陷编号（`docs/07` 的 D-xx / 验收报告 F/R 编号），写清根因与改法；
- 「新增什么证据」：能重跑的命令 + 原始输出 + 构建 SHA256（不允许只写"已验证"）；
- 「没修什么」：上一版已知限制里仍然成立的部分，逐条照抄，不许因为发了新版就悄悄删；
- `VERSION.txt` 的 `channel=rc.2`、`ga_ready=0`（`ga_ready=1` 只在 GA 包出现）。

### 8.4 谁定级、谁拍板

- **定级**：验收方（执行方可以提级建议，但不能自判「这条不严重」）；
- **发不发**：O0 拍板；阻塞级出现时执行方**立即上报**，不得先把 rc.2 发出去再汇报；
- **闭环判据**：缺陷在 `docs/07` 的「缺陷明细 / 本轮发现」里有编号、级别、修复与证据位置，
  只写「已修」不算闭环。
